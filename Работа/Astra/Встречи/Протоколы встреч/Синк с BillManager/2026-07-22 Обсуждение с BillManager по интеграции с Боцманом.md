## Протокол встречи



**Участники:** @Александр Шадрин, @Иван Мешков, @Юлия Луценко

### Две главные проблемы

1. **Контейнер изоляции** - в Brest это VDC (параллельно создаётся группа и пользователь). Изоляция - на уровне группы. Кто-то должен создавать и управлять этим
2. **IP-адрес для кластера** - нужно прокидывать floating IP для master-ноды

### Как это работает сейчас (со слов Фёдора из Boatsman)

@Александр Шадрин описал схему:
- Boatsman в конфигурации кластера получает логин/пароль пользователя для доступа к конкретному VDC
- Пользователь создан для конкретной организации, имеет доступ только к своему VDC
- Boatsman оперирует namespaces; IP получает через свой IPAM-модуль

### Что должен сделать BillManager до старта Boatsman

- Сходить в LDAP/ALDPro -> создать пользователя
- Сходить в Brest -> создать VDC
- Ассоциировать VDC с пользователем
- Передать логин/пароль пользователя в Boatsman
- IP-адреса: Boatsman решает через свой IPAM, BillManager может не участвовать

### Ключевой спор

@Иван Мешков: «Странная логика. Часть работы Boatsman делает сам с Brest (namespaces, IP), а часть закостылена в обработчики BillManager. Если Boatsman уже покрывает путь оркестрации, зачем сверху BillManager? Диссонанс».

Решение: BillManager обсудит внутри архитектурно, насколько это болезненно. Александр поставит встречу с Фёдором, чтобы прояснить почему Boatsman не берёт на себя полный путь.

## Решения

- **VDC + пользователь** - создаётся через BillManager перед запуском Boatsman
- **IP-адреса** - Boatsman решает через свой IPAM, BillManager не участвует
- **Следующая встреча** - среда, после получения модуля от Фёдора (пятница)

## Анализ встречи 2026-07-22

### Главный тезис

BillManager оказался в роли «прокладки» для Boatsman: создаёт VDC + пользователя, передаёт креды, а дальше Boatsman работает сам. Это создаёт архитектурный диссонанс - Boatsman уже умеет управлять namespaces и Brest напрямую, но часть пути вынужден проходить через BillManager. Команда BillManager сама не понимает, зачем им эта роль.

### Расхождение с текущей концепцией

- **BillManager как оркестратор для Boatsman** - противоречит целевой архитектуре, где оркестрацией должен заниматься IaaS Orchestrator, а BillManager - только биллинг. Но IaaS Orchestrator появится только в 2.3 (февраль 2027)
- **VDC + пользователь создаются BillManager** - в целевой картине это делает TMS через оркестратор. Здесь BillManager временно выполняет функцию, которая в будущем должна быть у TMS
