### Решение: идём без BillManager

@Андрей Крюков открыл встречу: **Сергей принял решение двигаться без BillManager**. Схемы с BillManager убираются, целевая архитектура пересматривается. Биллинг появится где-то сбоку позже - как подключать (сами / BillManager / CloudMaster) - вопрос второй.

### Квоты (Quota Manager)

Новая подсистема управления квотами:

- Квоты привязаны к **тенантам** (не к пользователям/группам Бреста)
- Каждый функциональный сервис описывает свои квоты - Quota Manager подтягивает их
- **Сценарий:** оркестратор при создании ресурса делает мгновенную проверку квот. Если превышение -> запрет. Если ОК -> создаёт -> уведомляет Quota Manager (нарастить счётчики)
- **Блокировка тенанта:** при превышении квоты -> TMS меняет статус тенанта на «заблокирован»
- **Иерархия:** первый этап - квоты на тенант. В будущем - квоты на организацию

**Дискуссия: квоты vs метринг**

@Максим Югай: не будет ли квоты связаны с метрингом? Достижение границ квот - процесс не в один шаг.

@Виталий Козловский: метринг даёт понимание красной зоны по ресурсам -> можно автоматически понижать квоты. При overprovisioning это актуально.

@Андрей Крюков: квоты - чисто технический инструмент оператора. Метринг - отдельная сущность для учёта потребления. Не связаны напрямую.

@Александр Шадрин: кейс Яндекса - системные квоты явно прописаны, хочешь больше -> отдельный разговор с провайдером. Квоты не про финансы, а про ограничение потребления.

**Итог:** квоты - технический инструмент для оператора. Без метринга, без привязки к контрактам. Потребитель ими не управляет (на первом этапе).

### IAM - текущее состояние и планы

@Андрей Крюков представил обзор:

**Сейчас:**
- Брест + ALD Pro - Kerberos
- RuBackup - LDAP
- BillManager, Astra Monitoring, APOS, Boatsman - OpenID Connect через IAM (RooX UIDM)

**Планируется:**
- FreeIPA заменит ALD Pro
- Централизованная валидация токенов через шлюз (проверка целостности, срока, отзыва)
- Делегирование аутентификации для сервисных аккаунтов (Brest -> SDN, оркестратор -> IAM)
- Перенос авторизации на шлюз (частично, Zero Trust)

### API Gateway и Zero Trust

@Ольга Милащенко: на схемах не хватает API-слоя между порталами и компонентами. Оркестратор не должен быть распылён.

@Александр Шадрин: API Gateway занимается роутингом и рейт-лимитингом. Подсистемы реализуют бизнес-логику сами. Gateway + BFF перед порталами.

**Zero Trust:** @Александр Шадрин подсветил - если авторизация только на шлюзе, злоумышленник внутри сети может curl'ом стучаться к сервисам. Должна быть авторизация на каждом сервисе. @Андрей Крюков подтвердил: Zero Trust - принцип платформы. Шлюз снимает часть проверок, но не все.

### BillManager: подтверждение

@Александр Шадрин: сегодня на встрече BillManager **прямо сказал - оркестрация не их путь**. Интеграция с одной системой - ок, с двумя-тремя - отказ. ВДЦ с интеграцией Brest + ALD Pro они считают костылём.

@Андрей Крюков: «Прекрасно. Это как раз нас направляет на правильное взаимодействие - через оркестраторы.»

## Решения

- **Без BillManager** - целевая архитектура пересматривается, биллинг сбоку
- **Квоты** - технический инструмент оператора, привязаны к тенантам, не к пользователям Бреста
- **Квоты ≠ метринг** - разные сущности
- **Zero Trust** - авторизация на каждом сервисе, шлюз снимает только часть проверок
- **BillManager** - не оркестратор (подтверждено ими самими)

## Риски

- **Zero Trust vs текущая схема развёртывания** - 🟠 если сервисы на ВМках без per-service авторизации - дыра в безопасности

## Анализ встречи 2026-07-22

### Главный тезис

Принято стратегическое решение идти без BillManager - то, что обсуждалось на серии 2 как «хотелось бы», стало реальностью. Встреча с BillManager сегодня это подтвердила: они сами не хотят быть оркестратором. Архитектура квот, IAM и шлюзов теперь строится в новой парадигме.

### P0 - блокеры

1. **Архитектура без BillManager не нарисована.** Целевая картина с тремя слоями (Пронюшкин) плюс биллинг сбоку - нужно формализовать.

### Расхождение с текущей концепцией

- **Квоты привязаны к тенантам** - OK, соответствует концепции platform-architecture (квоты - платформенная capability)
- **Квоты ≠ метринг** - раньше обсуждалось что метринг нужен для квот. Андрей Крюков развёл: квоты - технический инструмент, метринг - для расчёта стоимости
