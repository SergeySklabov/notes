## Протокол встречи



**Тема:** Новая архитектура ACP: порталы, TMS, IaaS-оркестратор, API Gateway, тенантная модель
**Участники:** @Андрей Крюков, @Максим Югай, @Михаил Перевалов, @Андрей Иволга, @Александр Шадрин, @Дмитрий Попенов, @Ольга Милащенко, @Сергей Склабовский

### Контекст

Андрей Крюков представил новую архитектуру ACP 2.2 и дальнейших релизов. Ключевой сдвиг - отказ от BillManager как центрального оркестратора и переход к собственным компонентам платформы.

**Ограничения презентации:** изменения показаны без привязки к релизам, биллинг/квоты/учёт потребления - вторая серия (ориентировочно в четверг).

### Новая архитектура: ключевые подсистемы

**Добавляются (зелёным на схеме):**

1. **Портал оператора** - новый портал для провайдера. Нужен, потому что управление тенантами - функция оператора, а не самообслуживания.
2. **Портал самообслуживания** - для потребителей. Управление ВМ, образами, дисками, сетями (база для Lika).
3. **Подсистема контейнеризации** - интеграция с Boatsman.
4. **IaaS-оркестратор** - провиженинг ресурсов (ВМ, диски, сети через APOS). База - прототип Александра Шадрина (нужно доделать образы и сети).
5. **API Gateway (подсистема предоставления программных интерфейсов)** - внутренний шлюз для единой точки доступа к сервисам + внешний шлюз (Terraform, CLI).
6. **TMS (Tenant Management System)** - управление жизненным циклом тенантов.

### Ключевые обсуждения

**1. Отказ от BillManager как оркестратора**

- BillManager закрывал порталы, биллинг, оркестрацию, отчётность - концентрация функций.
- Решение: оставить BillManager только биллинг (договоры, организации, тарифы, расчёт, выставление счетов).
- Провиженинг вынести в IaaS-оркестратор.
- Причина: продуктовая команда BillManager развивается по своей стратегии, не коррелирующей с нашей.

**2. TMS - новый центр платформы**

- TMS управляет тенантами: создаёт, хранит состояние, инкапсулирует реализацию во всех нижележащих подсистемах.
- Создание тенанта - растянутый процесс: TMS создаёт ID -> область в IAM/UIDM (+ роль пользователю) -> VDC в Бресте -> контейнер в APOS.
- **Важно:** TMS - единственный, кто знает о маппинге tenant_id ↔ VDC_id ↔ APOS_container.
- Оркестратор не управляет тенантами - только ресурсами внутри тенанта.
- **Дискуссия (Максим Югай):** TMS становится «вторым оркестратором под старым названием». Риски:
  - Дублирование адаптеров (TMS + IaaS-оркестратор -> Брест, APOS)
  - TMS начинает знать о ресурсах (кластеры, гипервизоры), растёт связанность
  - При появлении новых оркестраторов (PaaS, K8s) паутина интеграций будет множиться
- **Контраргумент (Александр Шадрин):** в новом подходе инкапсуляция правильная - никто извне не управляет состоянием TMS. В старом (тонкий TMS) внешние системы дёргали ручки изменения статуса - архитектурно неверно.
- **Риск (Сергей):** при появлении организации, PaaS-оркестратора количество стрелок будет расти как паутина. Нужно продумать водораздел.

**3. Портал оператора и портал самообслуживания**

- Ольга Милащенко: это один портал с двумя ролевыми контурами (оперируют одними объектами).
- Андрей: физически разные экземпляры, на одной кодовой базе (как PaaS-решения).
- Ольга: создание тенанта через портал оператора напрямую - непонятно пользователю. Тенант должен рождаться из объектов реального мира (договор, клиент, услуга).
- Андрей: сознательно упростил - фокус на отработке механики TMS + оркестратор. В Lika механика будет привязана к реальным сценариям.

**4. API Gateway (внутренний и внешний)**

- **Внутренний шлюз:** единая точка входа для общения с внутренними сервисами. Централизует проверку токенов, политики доступа.
- **Внешний шлюз:** для поставщика (Terraform, CLI), не для потребителя.
- **Александр Шадрин (опасения):**
  - Точка отказа (SPOF) - весь трафик через шлюз
  - Авторизация на шлюзе vs. в каждой подсистеме: если решение на шлюзе, то трафик между шлюзом и подсистемой «дырявый» (sidecar required)
  - Gravitee лежит мёртвым грузом (лицензионные ограничения, сложность развёртывания, проблемы с маршрутизацией)
  - Нужно пересмотреть выбор Gravitee или искать более подходящее решение
- **Андрей:** изменения в одном месте (централизация) vs. во всех подсистемах. Можно сделать защищённый контур.
- **Максим Югай:** ребята из IAM готовы поделиться документацией по интеграции со шлюзами. Авторизация на шлюзе - целевая картина.

**5. Безопасность и авторизация (Дмитрий Попенов / Александр Шадрин)**

- Дмитрий Попенов: предложенная архитектура не учитывает требования безопасности ОС - идентификация/авторизация пользователей должна сквозной проходить в каждую подсистему (Libvirt через Kerberos/сертификаты).
- Александр: с безопасниками обсуждали - запросы от пользователя должны пробрасываться от фронта до конечной подсистемы.
- **Решение:** согласовать подход с ДИБ (отдел безопасности) - где будет проверяться авторизация (на шлюзе или в каждой подсистеме). Сергей/Александр формулируют вопрос и идут к ДИБ.

**6. TMS - перепроектирование**

- TMS изначально проектировался с BillManager как оркестратором - теперь нужно перестраивать.
- Сергей: TMS в текущих требованиях был минимальным. Теперь расширяем функциональность, некоторые ручки API уберём (внешнее управление состоянием), добавим логику внутренних вызовов (Брест, APOS).
- Александр: внешне интерфейсы TMS не меняются (создать/удалить тенант), но внутренняя логика расширяется - «сходить в Брест и APOS».
- Максим Югай: TMS становится ядром платформы + меньше координации между командами. Но: растёт связанность, дублирование адаптеров, при появлении новых сущностей (организации) всё усложняется.

## Решения

- **BillManager** - только биллинг; провиженинг выносится в IaaS-оркестратор
- **TMS** - владеет жизненным циклом тенантов; инкапсулирует маппинг tenant -> VDC -> APOS_container
- **IaaS-оркестратор** - управляет ресурсами (ВМ, диски, сети), не тенантами
- **Внутренний API Gateway** - единая точка входа; вопрос авторизации (на шлюзе vs. в подсистемах) - согласовать с ДИБ
- **Gravitee** - пересмотреть как кандидата для API Gateway (лицензии, сложность)
- **Порталы** - два экземпляра (оператор + самообслуживание), одна кодовая база
- **Создание тенанта** - не через прямой UI оператора, а через бизнес-сценарии (Lika)
- **TMS: перепроектирование** - расширение внутренней логики, сужение внешнего API
- **Авторизация** - сформулировать вопрос и согласовать с ДИБ (формулировку готовит Александр Шадрин)

## Анализ встречи 2026-07-07

### 5 главных тем

1. **BillManager -> только биллинг.** Провиженинг выносится в IaaS-оркестратор. Причина: стратегия BillManager не коррелирует с нашей.
2. **TMS - центр платформы.** Управляет ЖЦ тенантов, инкапсулирует маппинг VDC/APOS. Спор: становится «вторым оркестратором» с дублированием адаптеров.
3. **Порталы: один или два.** Решено: два экземпляра (оператор + самообслуживание) на одной кодовой базе.
4. **API Gateway: внутренний + внешний.** Централизация проверки токенов vs. SPOF и «дырявый» трафик. Gravitee под вопросом.
5. **Безопасность: авторизация на шлюзе или в подсистеме.** Требуется согласование с ДИБ.

## AAR (After-Action Review)

### 1. Что планировали?
Презентовать новую архитектуру ACP 2.2-2.3, получить обратную связь, выявить противоречия концептуального характера.

### 2. Что получилось?

**Удачно:**
- Чётко сформулирован отказ от BillManager как оркестратора - ключевой архитектурный сдвиг
- TMS определён как центр управления тенантами с инкапсуляцией реализации
- Подняты и зафиксированы риски: связанность TMS, дублирование адаптеров, авторизация
- Достигнута договорённость по порталам (два экземпляра, одна кодовая база)
- Максим Югай включился как ТПМ - видит риски и предлагает проработку границ

**Неудачно:**
- Вопрос безопасности (Дмитрий Попенов) не был проработан до встречи - архитектура не согласована с ДИБ
- Вопрос авторизации (шлюз vs. подсистемы) остался открытым - требует отдельного похода к ДИБ
- Gravitee выбран без проверки лицензионных ограничений - лежит мёртвым грузом
- Границы TMS vs. IaaS-оркестратор размыты - риск дублирования адаптеров
- Биллинг/квоты/учёт потребления вынесены во вторую серию - без них картина неполная

### 3. Почему?
- Безопасность и ДИБ традиционно подключаются постфактум, а не на этапе архитектурного проектирования
- Gravitee выбирался «на вырост» без pilot-развёртывания и проверки лицензий
- Разделение TMS и оркестратора эволюционировало в ходе самой встречи - изначально не было чёткого водораздела
- BillManager-зависимость тянулась годами, решение отказаться созрело только сейчас

### 4. Что будем делать иначе?
- **Перед архитекурной встречей - пре-чекин с ДИБ.** Согласовать подход к авторизации до фиксации архитектуры.
- **API Gateway - провести PoC.** Gravitee или альтернатива: pilot с реальными сценариями до выбора.
