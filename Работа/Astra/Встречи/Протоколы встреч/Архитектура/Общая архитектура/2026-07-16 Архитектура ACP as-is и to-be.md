## Протокол встречи



**Тема:** Ознакомительная встреча - обзор текущей архитектуры ACP и целевого видения на 2.2/2.3+
**Участники:** @Сергей Склабовский, @Андрей Крюков, @Александр Шадрин, @Андрей Иволга, @Виталий Козловский, @Данил Борчевкин, @Дмитрий Малимон, @Прохор Акимцев, @Максим Югай, @Олег Головешко, @Тимур Гайнулин

### Контекст

Встреча для команды разработки - @Андрей Крюков представил архитектуру ACP: как устроена сейчас (as-is), какие проблемы выявлены, что планируется в 2.2 и куда движемся в 2.3+. Серия таких встреч будет продолжаться по мере проработки отдельных направлений.

### Предыстория и проблемы as-is

@Андрей Крюков начал с предыстории: платформа строилась как интеграция готовых продуктов группы «Астра». Предполагалось, что продуктовые команды будут реализовывать требования платформы. На практике:

- У продуктов своя стратегия, которая часто не пересекается со стратегией платформы, а有时 противоречит
- Требования платформы не учитываются в дорожных картах продуктов
- Продуктовые команды не заинтересованы - платформенные требования для них дополнительная нагрузка
- Проблемы неустранимы в текущей парадигме

### Текущий состав подсистем (as-is)

@Андрей Крюков выделил функциональные подсистемы:

- **Портал оператора** - совокупность всех панелей управления продуктов (BillManager, Brest, ALD Pro, RooX UIDM)
- **Портал самообслуживания** - интерфейс для конечных потребителей
- **Виртуализация** - Brest (ВМ, диски, сети)
- **Биллинг** - BillManager (фактически комбайн: биллинг + отчётность + портал + провиженинг)
- **Управление сетями** - SDN (APOS)
- **Резервное копирование** - RuBackup (только для платформы, не услуга)
- **Мониторинг** - Astra Monitoring (только платформа, не услуга)
- **Развёртывание/настройка** - ACP Installer
- **IAM** - был просто ALD Pro как каталог, сейчас эволюционирует в полноценную IAM

### Что даём потребителю сейчас

- Только **виртуальные машины** как услуга
- На подходе - **контейнеры** (Kubernetes)
- Сети и хранение - только поддерживающие функции для ВМ, не самостоятельные услуги

### План на ACP 2.2

- **Новые порталы** (оператора и самообслуживания) - MVP, жёлтый уровень (в границах платформы, но не готовы заказчикам)
- **Tenant Management (TMS)** - закладываем понимание тенанта, пока ни с кем не интегрирован. Причина: BillManager не берёт требования
- **Контейнеризация (Boatsman)** - новая услуга: managed Kubernetes. Boatsman интегрирован с Brest (сам управляет ВМ), будет интеграция с BillManager для биллинга и с IAM для SSO
- **BillManager** - сокращаем его роль до **только биллинга**. Убираем из него функции личного кабинета, портала и оркестратора

### План на ACP 2.3+

- **IaaS Orchestrator** - забирает провиженинг ресурсов у BillManager. Управляет созданием ВМ, дисков, сетей через Brest и SDN. Автоматизирует связку сеть-ВМ (сейчас руками)
  > **Обновление (20.07, встреча с RnD):** подтверждено окно 2.3 - Libvirt 1.8.8 (февраль 2027). Подробнее: [[2026-07-20 Встреча с RnD]]
  > **Обновление (21.07, вторая серия архитектуры):** 2 варианта 2.3 архитектуры. Из BillManager убираем оркестрацию и квоты. Подробнее: [[Архитектура/Общая архитектура/2026-07-21 Архитектура ACP 2.3 - вторая серия|2026-07-21 Архитектура ACP 2.3]]
- **API Gateway (APIM/Gravitee)** - внутренний шлюз для безопасности и роутинга внутри платформы + внешний для публикации API (Terraform, CLI). Интегрирован с IAM (проверка токенов OpenID Connect)
- **Платформенные сервисы** - IAM, TMS, квоты, мониторинг. Любой функциональный сервис должен быть с ними интегрирован
- **Событийная архитектура** - шина событий как основа взаимодействия
- **Новые услуги:** сетевые (маршрутизация, DNS, группы безопасности), хранение (блочное TROK + объектное S3), управляемые контейнеры

### Обсуждение: Gravitee (APIM)

@Данил Борчевкин: почему Gravitee снова в архитектуре? Полтора года назад он уже был, от него отказывались, теперь снова вернулись. Команда не нанята, стек (Java) чужой для департамента.

@Александр Шадрин пояснил: из Gravitee используется только API Gateway (роутинг трафика). На одной ВМ с Unified API. Доработки не требуются, Java-команда не нужна. Gateway остаётся, но фокус сузился - только шлюз безопасности, никакой API-экономики. Возможна замена в будущем.

@Сергей Склабовский: вынести на отдельную встречу - @Александр Шадрин покажет, что именно было сделано и почему такое решение.

### Обсуждение: BillManager

@Данил Борчевкин: почему BillManager не может быть просто выкинут? Есть административные и организационные договорённости, которые его удерживают.

@Сергей Склабовский: мы не отказываемся от BillManager полностью. Он остаётся как **биллинг** (выставление счетов, квотирование, подписки). Убираем его функции личного кабинета и оркестратора, чтобы ослабить связанность.

@Александр Шадрин добавил: вынос оркестрации позволит пробрасывать контекст пользователя (важно для МКЦ/МРД) и усилить безопасность - проверка на стороне Brest.

### Обсуждение: IAM и RooX

@Данил Борчевкин: IAM разрабатывается сторонней компанией (RooX) - мы не нарабатываем экспертизу внутри, платим внешнему вендору. Как и с SDN (Ingree). Рано или поздно придётся заносить обратно, но время будет упущено.

@Сергей Склабовский: вопрос в бюджетах. Моё мнение - нужно затягивать разработку внутрь. Но решение не на этом уровне.

### Обсуждение: Сертификация

@Дмитрий Малимон подсветил риски:
- Если компонент безопасности (IAM) разрабатывает внешний вендор (RooX), его сертификация - полный цикл как для ОС (ПМИ, документация по безопасности, тестирование кода)
- Это не вопрос месяцев, может занять годы
- Нужно консультироваться с ДИБ и Ольгой Рябикиной

@Сергей Склабовский: платформа не сертифицируется целиком. Сертифицируются отдельные компоненты, в которых есть функции безопасности (IAM будет сертифицирован). Мы платим RooX - они заверили, что компонент будет сертифицирован. С ДИБ общаемся регулярно.

@Максим Югай: мы осознанно отказались от Open Source решений (Keycloak) именно из-за бремени сертификации. Выбрали RooX, у которых есть опыт прохождения сертификации. Они берут на себя ответственность за сертификацию обновлённых версий.

## Решения

- **Направление развития** - презентация задаёт вектор, архитектура будет уточняться по каждому компоненту отдельно
- **BillManager** - остаётся как биллинг; функции портала, оркестратора и ЛК выносятся в новые подсистемы
- **Gravitee (APIM)** - остаётся как минимальный API Gateway (роутинг), может быть заменён
- **API Gateway** - два контура: внутренний (безопасность/роутинг) и внешний (Terraform/CLI)
- **IAM / RooX** - вопрос инсорсинга не решён, упирается в бюджеты
- **Сертификация** - не все компоненты подлежат сертификации, только с функциями безопасности. IAM сертифицируется силами RooX

## Риски

- **IAM/RooX** - 🟠 разработка критического компонента безопасности у внешнего вендора без наращивания внутренней экспертизы
- **BillManager dependency** - 🟠 организационные и административные договорённости могут блокировать сокращение его роли
- **Сертификация IAM** - 🟠 если RooX не пройдёт сертификацию в заявленные сроки - сдвиг платформы
  > **Обновление (20.07, встреча с RnD):** TROK сертификация через Maim Plus (~1 год), IAM в Brest с пересертификацией (май 2027). Подробнее: [[2026-07-20 Встреча с RnD]]
- **Gravitee (APIM)** - 🟡 непрофильный стек (Java) - если потребуются доработки, придётся нанимать команду
- **Тенанты без интеграции** - 🟡 TMS в 2.2 без интеграции с подсистемами - рискуем построить изолированный компонент

## Анализ встречи 2026-07-16

### 5 главных тем

1. **As-is: интеграция продуктов не работает** - продуктовые команды не мотивированы выполнять требования платформы, стратегии расходятся
2. **BillManager - комбайн, который надо разобрать** - биллинг остаётся, остальное выносим в IaaS Orchestrator и новые порталы
3. **Платформенный подход вместо интеграции** - платформенные сервисы (IAM, TMS, квоты, мониторинг) + событийная архитектура
4. **IAM и сертификация** - RooX как вендор IAM несёт бремя сертификации, но вопрос инсорсинга остаётся
5. **Gravitee - символ неопределённости** - решение то принимается, то откладывается, команда не нанята

## AAR (After-Action Review)

### 1. Что планировали?
Ознакомительная презентация архитектуры ACP для команды: as-is, проблемы, целевое видение на 2.2 и 2.3+.

### 2. Что получилось?

**Удачно:**
- @Андрей Крюков системно изложил всю картину - от предыстории до целевой архитектуры
- Команда активно задавала вопросы - вскрыты реальные риски (сертификация, Gravitee, BillManager)
- Подтверждён вектор: платформенный подход вместо интеграции продуктов

**Неудачно:**
- Технические проблемы с демонстрацией экрана (вместо слайдов показывал список)
- Не хватило времени на сертификацию - тема поднята, но не раскрыта
- Не прозвучали сроки по ключевым вехам (когда IaaS Orchestrator, когда замена Gravitee)

### 3. Почему?
- Первая встреча серии - фокус на общую картину, детали вынесены
- Вопрос сертификации всплыл как cross-cutting - потребует отдельной серии
- Проблемы с sharing - организационные

### 4. Что будем делать иначе?
- **Следующие встречи** - фокус на конкретный компонент со сроками и ADR
- **API Gateway встреча** - @Александр Шадрин организует отдельно
- **Сертификация** - @Сергей Склабовский организует встречу с ДИБ
