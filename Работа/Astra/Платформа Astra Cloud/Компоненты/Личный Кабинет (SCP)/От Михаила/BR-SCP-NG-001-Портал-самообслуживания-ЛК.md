## Положение о бизнес требовании

### Исходные данные

В настоящее время управление ресурсами облачной платформы ACP осуществляется через BillManager — legacy-интерфейс, совмещающий функции биллинга и презентационного слоя. BillManager не является cloud-native решением: пользователь вынужден выбирать тарифный план перед созданием ресурса, интерфейс не соответствует современным стандартам UX, отсутствует единая точка входа для самообслуживания.

Параллельно ведётся разработка IaaS-оркестратора (Александр Шадрин) — нового компонента, который берёт на себя управление жизненным циклом ресурсов (ВМ, диски, сети) и предоставляет единый REST API. IaaS-оркестратор готов по следующему функционалу:
- Управление ВМ (CRUD, стоп/старт/рестарт, resize)
- Управление дисками (CRUD, attach/detach)
- Управление сетями (Brest, read-only)

На архитектурном созвоне 25.06.2026 подтверждено: BillManager выводится из контура MVP, IaaS-оркестратор становится платформенным оркестратором для нового портала самообслуживания.

### Возможности бизнеса

**Целевая аудитория:** клиенты (тенанты) облачной платформы ACP — организации и их пользователи, которым необходимо самостоятельно управлять виртуальными ресурсами без обращения к оператору.

**Бизнес-задачи, которые решаются:**

1. **Самостоятельное создание ВМ** — пользователь через Web-интерфейс создаёт виртуальную машину: выбирает ОС, конфигурацию (vCPU/RAM), диски, сеть, SSH-ключ. Без звонков оператору, без заявок в техподдержку.

2. **Управление жизненным циклом ВМ** — запуск, остановка, перезагрузка, изменение конфигурации, удаление. Полный контроль над ресурсами.

3. **Управление дисками** — создание дополнительных дисков, прикрепление к ВМ, открепление, удаление. Гибкое управление хранилищем.

4. **Просмотр и мониторинг** — дашборд с состоянием ресурсов, список ВМ/дисков/сетей, детальная информация по каждому ресурсу.

5. **Авторизация через SSO** — единый вход через IAM (RooX/RUKS IDIAM), выход (SLO), отображение роли и тенанта.

**Преимущества для продукта:**
- Соответствие стандартам Cloud Native: пользователь выбирает ресурсы, а не тарифы (как в Yandex Cloud, Selectel, Cloud.ru)
- Снижение нагрузки на операторов поддержки за счёт self-service
- Единый портал для всех клиентов ACP вместо нескольких разрозненных интерфейсов
- Возможность наращивать функциональность (PaaS, K8s, backup) в последующих релизах

**Отрицательные последствия отказа от реализации:**
- ACP остаётся с legacy-интерфейсом BillManager, который не отвечает ожиданиям современных пользователей облачных платформ
- Проигрыш конкурентам (Yandex Cloud, Selectel, VK Cloud) по UX и скорости предоставления ресурсов
- Усложнение внедрения новых сервисов (PaaS, K8s) — каждый новый сервис потребует доработки BillManager

### Особенности развертывания

**Режим работы:** 24×7, портал должен быть доступен постоянно (время недоступности не более 99.9% в рамках SLA платформы).

**Численность пользователей:** на старте MVP — единицы тенантов (пилотные клиенты), до 100 одновременных пользователей. В перспективе — до 5000+ concurrent users.

**Квалификация персонала:** пользователи — технические специалисты клиентов (DevOps, системные администраторы), знакомые с облачными технологиями. Администраторы — операторы платформы ACP.

**Риски целостности данных:**
- Операции создания/удаления ресурсов необратимы и влияют на инфраструктуру клиента
- Все операции должны логироваться с request_id для аудита
- Необходима защита от случайного удаления (диалоги подтверждения)
- Сессии пользователей должны быть защищены (SLO при выходе)

**Системный ландшафт:**
- Фронт: Nuxt 4 + PrimeVue, развёртывается через контейнеры (Docker/K8s)
- Бэкенд: IaaS-оркестратор (REST API), IAM (RooX/RUKS IDIAM), Brest (OpenNebula)
- Сети: Brest (MVP), APOS/SDN (post-MVP)
- Интеграции: IAM (OIDC), IaaS-оркестратор (REST API), BillManager (read-only потребление)

**Время реакции:** загрузка страниц — не более 2 секунд. Операции создания ВМ — асинхронные (до 2-3 минут). Операции с дисками — до 30 секунд.

### Модель бизнес-процесса (необязательное)

**AS IS (текущий процесс):**
```
Клиент → Заявка оператору → Оператор создаёт ресурс в BillManager → Клиент получает доступ через BillManager → 
Выбирает тариф → Создаёт ВМ
```

**TO BE (целевой процесс в MVP):**
```
Клиент → Вход в ЛК через SSO (IAM) → Дашборд → Создание ВМ (выбор ОС, конфигурации, диска, сети, SSH-ключа) → 
Асинхронное создание через IaaS-оркестратор → ВМ готова → Управление (стоп/старт/рестарт/resize/диски)
```

### Критерии успеха

1. **MVP (релиз ACP 2.2.0, ноябрь 2026):** пользователь может выполнить полный цикл: войти → увидеть дашборд → создать ВМ с диском → управлять ВМ (стоп/старт/стоп) → удалить ВМ. Диски: создать, прикрепить к ВМ, открепить, удалить. Сети: просмотреть.

2. **Критерии качества:**
   - Время загрузки дашборда < 2 сек (при 100 concurrent users)
   - Все операции с ресурсами — асинхронные с отображением прогресса
   - Единый формат ошибок (error_code/error_message)
   - pass-парольная аутентификация через IAM (SSO)
   - Полноценный выход (SLO) с завершением сессии на стороне IAM

3. **Критерии функциональной полноты (23 P0 US):**
   - Auth: вход, выход, роль, восстановление пароля
   - Dashboard: главный экран, список сервисов
   - VM: список, детали, создание, удаление, resize, стоп/старт/рестарт
   - Disks: список, создание, удаление, attach/detach
   - SDN: список сетей, выбор сети при создании ВМ
   - Images: каталог образов, выбор при создании ВМ
   - SSH: управление ключами

### Риски, предположения и зависимости, ограничения

**Критические риски:**
| Риск | Влияние | Митигация |
|------|---------|-----------|
| OpenAPI-спецификация IaaS не готова — фронт не может стартовать | Блокирует весь MVP | Запросить черновик до 30.06 |
| IAM 2.1 не готов — нет JWT claims (tenant_id, роль) | Блокирует авторизацию | Минимальный viable JWT (4 claims) до 30.06 |
| Quota Management не существует — нет квот | Блокирует проверку лимитов | Заглушка на фронте; назначить владельца |
| UI-kit не выбран | Блокирует дизайн | PrimeVue — вероятный кандидат |

**Предположения:**
- Тенант создаётся оператором вручную (не в MVP)
- 1 тенант = 1 пользователь в MVP (мультитенантность — post-MVP)
- Сеть (Brest) создаётся автоматически при создании тенанта
- Системный диск — неотъемлемая часть ВМ (boot-диск нельзя открепить)
- Образы ОС предоставляются платформой (публичные), пользовательские — post-MVP

**Зависимости:**
- IaaS-оркестратор (Шадрин) — все US по ВМ, дискам, сетям
- IAM (Югай) — US-AUTH-01..04
- SDN/APOS (Иволга) — US-SDN-01..05 (APOS — post-MVP)
- BillManager — US-BIL-001 (потребление, P1)

**Ограничения:**
- MVP — только Web UI (без CLI, Terraform, API-ключей)
- MVP — только Brest-сети (APOS/SDN — post-MVP)
- MVP — без создания тенантов (только оператор)
- MVP — без backup/снимков ВМ
- MVP — без управления安全 группами (read-only если есть)
