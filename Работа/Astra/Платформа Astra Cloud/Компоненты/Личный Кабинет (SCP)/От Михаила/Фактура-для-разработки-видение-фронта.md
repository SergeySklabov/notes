## 1. Vue vs React — почему мы здесь

### Выбор сделан: Nuxt 4 (Vue 3)
*Решение принято, не обсуждается на этой встрече. Нужно объяснить «почему», чтобы разработка понимала контекст.*

| Критерий                        |             Nuxt 4 (Vue 3)             |         React (Next.js)         |
| ------------------------------- | :------------------------------------: | :-----------------------------: |
| **SSR из коробки**              |                  ✅ Да                  |              ✅ Да               |
| **Скорость старта**             |    Высокая — 1 неделя до первой US     |  Средняя — нужно собрать стек   |
| **Файловый роутинг**            |        ✅ Встроенный, без config        |    ✅ App Router, но verbose     |
| **Экосистема на платформе**     | ✅ Уже используется: `test-mvp` на Nuxt |            ❌ С нуля             |
| **State management**            |      Pinia (простой, TypeScript)       |  Zustand/Redux (ещё выбирать)   |
| **Кто пишет**                   |      Та же команда, что и сейчас       |     Нужно учить / нанимать      |
| **Микрофронтенды (цель 2027+)** |    Module Federation + Nuxt Layers     |   Module Federation + Next.js   |
| **UI-kit**                      |        PrimeVue 4 (уже выбран)         | PrimeReact — есть, но зрелость? |

**Итог:** Nuxt 4 — рациональный выбор под нашу задачу:
- 30+ страниц — файловый роутинг даёт структуру без боли
- Pinia проще Redux/Zustand для команды без React-опыта
- Единый стек (Vue + PrimeVue) — разработчику не нужно переключаться между разными технологиями в рамках одного портала
- Миграция на микрофронтенды возможна через Nuxt Layers + Module Federation

**Про SSR:** в таблице выше строка «SSR из коробки» — это констатация факта (обе технологии его имеют), а не наше требование. Для портала самообслуживания (за авторизацией, сложный UI, SEO не нужен) SSR не даёт преимуществ, только усложняет деплой. Наш режим — `output: "static"` (SSG), если заказчик коробочной версии явно запросит SSR — вернёмся к вопросу (см. ADR).

## 2. Видение будущего портала: «кучу ЛК в один»

### Сейчас: фрагментация
*Несколько независимых интерфейсов — пользователь прыгает между ними:*

```
BillManager → свой интерфейс (старый)
Brest (Cristal) → свой интерфейс (OpenNebula)
IAM (RooX) → свой интерфейс
SDN → свой интерфейс
```

### Цель: ЕДИНЫЙ портал самообслуживания
*Одна точка входа. Разделы определяются ролями пользователя (RBAC).*

```
Один портал (ЛК / SCP)
├── Дашборд — сводка всего
├── ВМ — управление виртуальными машинами
├── Диски — блочные устройства
├── Сети — виртуальные сети
├── Образы — каталог ОС
├── SSH-ключи
├── Администрирование — тенанты, квоты, пользователи
└── Потребление — стоимость, метрики
```

## 3. Архитектура: Монолит vs Микрофронтенды vs Модули

### Два подхода — два времени

```
MVP (ноябрь 2026)            →  Цель (2027+)
Подход C: Гибрид/монолит     →  Подход B: Микрофронтенды
Nuxt 4, один репозиторий     →  Shell + независимые МФ
1 команда, 1 CI/CD           →  N команд, N CI/CD
Быстро (2-4 нед до US)       →  Масштабируемо
```

### Подход C (MVP): модульный монолит на Nuxt 4

```
tp-front/
├── app/
│   ├── pages/            ← файловый роутинг (30+ страниц)
│   ├── layouts/          ← default.vue = будущий Shell (навигация, RBAC)
│   ├── middleware/        ← auth.ts + rbac.ts (глобально)
│   └── stores/           ← Pinia: auth, tenant, navigation
├── modules/              ← будущие микрофронтенды
│   ├── vm/               ← IaaS (ВМ, диски, образы)
│   ├── sdn/              ← SDN (сети)
│   └── admin/            ← Админ-панель
├── shared/               ← будущий npm-пакет @tp/shared
│   ├── types/
│   ├── composables/
│   └── ui-kit/
└── server/api/           ← proto-BFF (агрегация профиля)
```

**Ключевое правило:** каждый модуль в `modules/` пишется изолированно.
- Модуль НЕ импортирует другие модули — только `shared/`
- Модуль НЕ использует store других модулей
- Коммуникация — только через URL и API

Когда приходит время выделить микрофронтенд — модуль уже готов.

### Подход B (цель): микрофронтенды

**Важное уточнение:** IaaS-оркестратор — единый компонент. Он сам агрегирует Brest (вычисления) + SDN (сети).  
**ЛК не нужно знать внутреннюю кухню IaaS** — оркестратор сам предоставляет ВМ, диски, сети, образы через свой API.  
~~Поэтому деление на микрофронтенды по доменам (IaaS / SDN) не имеет смысла — ЛК смотрит на один API.~~

Если когда-нибудь дойдём до микрофронтендов — скорее всего будет:

```
tp-shell (оболочка)           tp-mf-portal         tp-mf-admin
┌──────────────────────┐      ┌──────────────┐    ┌──────────────┐
│ layouts/default.vue  │      │  ВСЁ, что    │    │  Админ-      │
│ middleware/auth/rbac │      │  видит       │    │  панель      │
│ stores/auth/tenant   │      │  пользователь│    │  (тенанты,   │
│ mf-loader (Module    │      │  ВМ, диски,  │    │  квоты,      │
│   Federation)        │      │  сети,       │    │  пользователи│
│ UI-kit → @tp/shared  │      │  образы, SSH │    │  )           │
└──────────────────────┘      │  → IaaS API  │    │  → Priv API  │
                              └──────────────┘    └──────────────┘
                              @tp/shared (npm-пакет)
                              ┌────────────────────┐
                              │  types, composables │
                              │  ui-kit (Button,    │
                              │   Table, Modal...)  │
                              └────────────────────┘
```

## 4. Триггеры миграции: когда переходить от C к B

| Триггер | Что происходит | Действие |
|:-------:|---------------|----------|
| 👥 **3+ команды** работают с порталом | Merge-конфликты, блокировки | Выделить первый МФ |
| 📦 **50+ экранов**, 200+ компонентов | Кодовая база растёт | Разбивать на МФ |
| 🐌 **Релизы тормозят** | Один модуль блокирует другой | Выделить проблемный МФ |
| 🧪 **BFF уже введён** | Есть слой агрегации | Без BFF МФ сложнее |
| 🔄 **3+ типа фронтов** | ЛК + админка + мобилка | Полноценный BFF |

## 5. BFF — когда и зачем

**MVP:** без BFF. Фронт ходит напрямую в APIM.
proto-BFF на `server/api/` Nuxt — для агрегации профиля (1 запрос вместо 4-6).

**Цель (2027+):** отдельный BFF-сервис — когда появятся 2+ команды фронта или 3+ типа фронтов.
