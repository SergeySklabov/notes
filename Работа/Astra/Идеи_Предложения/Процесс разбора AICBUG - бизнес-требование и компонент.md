# Процесс разбора AICBUG: бизнес-требование + компонент + гейт ТПМ

## Проблемы

**Проблема 1. Решение принимается до подтверждения реализуемости.** На PBR говорят «берём», а в заведённом FR профильный ТПМ отвечает «решения нет». Потому что решение принимается до того, как ТПМ проверил реализуемость, и отрывается от контекста: нет линка AICBUG → FR.

**Проблема 2. Обязательные поля не заполнены.** Компонент не проставлен — тикет не роутится к профильному ТПМ. Бизнес-заказчик не указан — невозможно приоритизировать. PBR принимает тикет без адресата и контекста.

**Проблема 3. В тикет приходит решение вместо проблемы.** Коллеги (сейлы, КАМы, саппорт) пересылают конкретную реализацию, которую попросил клиент, минуя саму боль. Без заявленной проблемы тикет нельзя приоритизировать, оспорить решение или предложить альтернативу.

**Проблема 4. Поле «Проблема» заполнено, но не содержит проблемы.** Описание есть, но оно не проходит тест "не может / вынужден / теряет / сложно" - это техническое наблюдение, вопрос или констатация факта. Без формулировки «[роль] не может [действие]» непонятно, какая именно боль и для кого.

**Проблема 5. Запросы в вакууме.** FR заводят напрямую, минуя AICBUG и этап извлечения проблемы. Часть таких запросов могла быть решена на L2/L3 (поддержка) или оказаться кастомной историей под одного заказчика — но они уходят сразу в разработку без предварительного анализа.

## Предложение

### A. Обязательные поля + шаблон

Ключевое изменение: **проблема и решение клиента разведены в разные поля**. Клиенту нормально прийти с готовым решением - провал не в этом, а в том, что за ним никто не извлёк проблему.

| Поле | Обяз. | Что писать | Антипаттерн |
|---|---|---|---|
| **Проблема** | да | «[роль заказчика] не может [ценное действие], потому что [ограничение] -> [последствие]» | «реализовано ли X?», «клиент хочет [фичу]» |
| **Что просил клиент / источник** | да | Дословно - формулировка клиента, можно с его решением | пересказ своими словами |
| **Заказчик / организация** | да | Кто. Один клиент или платформенная проблема - меняет приоритет | пусто |
| **Триггер / срочность** | нет | Сделка / тендер / дедлайн / deal breaker - или internal-находка | пусто, когда за запросом стоит сделка |
| **Компонент ACP** | да | По коду из справочника - по нему тикет виден профильному ТПМ | «не знаю» |
| **Материалы** | нет | Письмо / ТЗ / выписка из тендера | «см. вложение» без выдержки |
| **Выдержка автора** | да, если есть | 2-4 предложения дословно с источником («ТЗ п.4.2») | пересказ вместо цитаты |
| **Ожидаемый результат** | да | Критерий готовности со стороны клиента | пусто |

**Тесты:** «Проблема» - если нет «не может / вынужден / теряет», это ещё не проблема, возврат автору. «Компонент» - если сейл не указал даже по справочнику, это сигнал лиду: нужен ликбез по карте компонентов.

### B. Процесс PBR

**Pre-PBR (за 2-3 дня до встречи):**
- PO / фасилитатор собирает накопившиеся AICBUG за месяц, группирует по компоненту, рассылает ТПМ.
- ТПМ проверяет тикеты своего компонента: заполнены ли обязательные поля (Проблема, Заказчик, Компонент), корректна ли формулировка проблемы (тест «не может / вынужден / теряет»).
- Если тикет не проходит — ТПМ оставляет комментарий с причиной («не указан компонент», «проблема не извлечена»). Тикет не попадает на встречу, автору — обратная связь.

**Встреча (ежемесячно):**
- Разбираются только тикеты, прошедшие pre-PBR.
- Для каждого тикета ТПМ выносит вердикт.

**Отмена встречи:**
- Если на месяц нет AICBUG или все отсеялись на pre-PBR — встреча не проводится.

### C. Гейт «подтверждение реализуемости ТПМ» ДО «берём»

На PBR решение фиксируется как статус `К проработке [COMPONENT]`:

- Профильный ТПМ выносит один из четырёх вердиктов:
  - **можно сходу** - заводим FR;
  - **нужен R&D** - заводим на проработку с оценкой;
  - **не мой компонент -> [X]** - передаём профильному ТПМ;
  - **нельзя** - с обоснованием, AICBUG закрывается.
- Только после вердикта «можно» / «R&D» заводится FR и линкуется с AICBUG.

**Enforcement (один из двух):**
- `К проработке [COMPONENT]` - реальный статус в Jira workflow, переход в «берём»/FR закрыт без вердикта ТПМ;
- либо фасилитатор PBR отклоняет тикеты без заполненных обязательных полей и без вердикта.

### D. Обязательный линк AICBUG -> FR

- FR не заводится без линка на исходный AICBUG (и наоборот).
- AICBUG нельзя закрыть без линка на FR / решение / вердикт «нельзя».

## Примеры «плохо -> хорошо»

### [AIC-2081](https://jira.astralinux.ru/browse/AIC-2081) - проброс GPU / vfio

**Как пришло:** флаги ядра + dmesg. Все бизнес-разделы пустые.
**Как надо:**
- **Проблема:** Клиент *[уточнить]* не может пробросить GPU целиком в ВМ с полной производительностью - без флагов MSI/MSI-X прерывания не работают.
- **Что просил:** автонастройка `enable_sriov=1`, `allow_unsafe_interrupts=1` при пробросе GPU.
- **Заказчик:** ⚠️ *не указан*
- **Компонент:** VIR (Brest).
**Что делать:** пока заказчик не указан - тикет с пометкой «internal R&D». На PBR профильный ТПМ VIR: вердикт «нужен R&D» (оценить автонастройку флагов). После вердикта - завести FR в VIR.

*Чему учит:* инженерный запрос без заказчика и триггера невозможно приоритизировать.

### [AIC-2084](https://jira.astralinux.ru/browse/AIC-2084) - сети в BILLmanager (ПСБ)

**Как пришло:** три «реализовать...», клиент ПСБ.
**Как надо:**
- **Проблема:** Сетевой инженер ПСБ не может *[уточнить]* при создании ВМ - BILLmanager подключает только одну сеть, IP назначаются вручную.
- **Что просил:** (1) несколько сетей при создании, (2) выбор IP из пула, (3) обратная синхронизация.
- **Заказчик:** ПСБ.
- **Компонент:** ⚠️ *BIL? BILLmanager декомпозируется.*
**Что делать:** компонент не BIL (уходящий) - передать ТПМ SCP. ТПМ SCP: вердикт «не мой компонент» или «нужен R&D» (строить в Self-Service Portal). После вердикта - завести FR в SCP.

*Чему учит:* запрос под одного клиента в уходящий компонент. Без извлечённой проблемы нельзя спросить «а надо ли строить иначе?».

### [AICBUG-124](https://jira.astralinux.ru/browse/AICBUG-124) - квота BILLmanager -> Brest

**Как пришло:** проблема *есть* (зависание при заказе сверх ресурсов), но заголовок сразу называет решение.
**Как надо:**
- **Проблема:** При заказе ресурсов больше, чем доступно в Brest, ВМ зависает - нет проверки.
- **Что просил:** связать квоту BILLmanager с ресурсами Brest.
- **Заказчик:** платформенная проблема.
- **Компонент:** ⚠️ *QuotaManager, пересекается с TMS.*
**Что делать:** передать ТПМ TMS (квоты). ТПМ TMS: «можно сходу» или «нужен R&D». После вердикта - завести FR с вариантами (административно / резервирование / проверка при заказе).

*Чему учит:* проблема видна -> обсуждаются альтернативы (контраст с [AIC-2084](https://jira.astralinux.ru/browse/AIC-2084)/[AIC-2081](https://jira.astralinux.ru/browse/AIC-2081)). Фикс: не зашивать решение в заголовок.

### [AICBUG-123](https://jira.astralinux.ru/browse/AICBUG-123) - группы клиентов (RBAC)

**Как пришло:** запрос-вопрос без бизнес-требования, без компонента - «Нет возможности работать с группами клиентов. Реализовано ли такое же? Надо протестировать.»
**Как надо:**
- **Проблема:** Администратор ACP не может управлять доступом на уровне групп клиентов - RBAC-модель не поддерживает иерархию -> права назначаются каждому пользователю отдельно, администрирование не масштабируется.
- **Что просил:** «Реализовано ли такое же для групп пользователей? Надо протестировать.»
- **Заказчик:** *[уточнить, автор Виктория Агафонова]*
- **Компонент:** IAM.
**Что делать:** заказчик не указан - выяснить через автора. Компонент IAM. На PBR ТПМ IAM: вердикт «нужен R&D» (RBAC в контексте перехода ALDPro -> FreeIPA). После вердикта - завести FR в IAM со ссылкой на [AICBUG-123](https://jira.astralinux.ru/browse/AICBUG-123).

*Чему учит:* проблема в описании есть, но не извлечена в отдельное поле -> тикет провис год без FR, без бизнес-заказчика, без движения. Компонент не проставлен -> некому было вынести вердикт.

## Итог одной фразой

В AICBUG обязательны **проблема (отдельно от решения) + заказчик + компонент**; на PBR - вердикт ТПМ до «берём»; FR слинкован с AICBUG. Запрос-решение без извлечённой проблемы веса не имеет.
