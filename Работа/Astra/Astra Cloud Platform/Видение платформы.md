# Description

Облачная Платформа Астра - это единое ядро для масштабируемого и управляемого предоставления облачных продуктов нашим конечным клиентам. 
Ключевыми целями создания облачной платформы являются:
- Монентизация виртуальных ресурсов за счет предоставления качественных сервисов, как самой виртуализации, так и IaaS/PaaS/SaaS в том числе за счет предоставления сервисов из ГК Астра и партнерских решений, обеспечивая при этом должный уровень маржинальности как собственных сервисов, так и сервисов партнёров
- Монетизации осуществляется за счет четырёх моделях поставки: **public** (как сервис из облака), **on-prem** (как продукт в контур клиента), **hybrid** (единое управление обеими моделями) и **multi-cloud** (управление нашими и сторонними облаками через единый API)
- Создание комплементарных фундаментальных сервисов облака (такие как IAM, Monitoring, Logging, Audit, Resource Manager), становящихся общим основанием для всех облачных продуктов и исключающих дублирование функциональности
- Обеспечение гарантированного уровня надёжности (SLA) и прозрачности состояния сервисов для клиентов.
- Автоматизация процессов компании, связанных с предоставлением клиентам облачных продуктов, а также сокращение ручных операций и времени вывода продукта
- Предоставление клиентам механизмов самообслуживания
- Реализация общих для всех продуктов механик: регистрация клиента, заказ продуктов и управление, тарификация и выставление счетов
- Унификация процесса вывода продуктов и сокращение time-to-market для новых продуктов за счёт готовых интеграций, общепринятых паттернов и переиспользуемых шаболнов (привет Dev Platform:)
- Обеспечение технологическая независимость за счет возможности смены продуктов (OpenNebula, Боцман и др.) без изменения клиентского API и бизнес-логики.

Функциональные блоки 
## Пользовательский слой (интерфейсы)
Это не отдельный блок, а точка входа. Компоненты здесь не содержат бизнес-логики, а только маршрутизируют запросы и отображают данные.
**Компонент П.1. Личный кабинет (UI)**  
• Что делает: предоставляет веб-интерфейс для клиентов: управление проектами, заказ услуг, просмотр счетов, мониторинг ресурсов.  
• Границы: не содержит бизнес-логики. Только отрисовка UI и вызов API. Не хранит состояние.  
• Зависит от: Внешнее API.
**Компонент П.2. Внешнее API (Public API)**  
• Что делает: публичный API для автоматизации: Terraform, CLI, интеграции партнёров. Принимает запросы, аутентифицирует, маршрутизирует в сервисы.  
• Границы: не содержит бизнес-логики. Только маршрутизация и базовая валидация. Не хранит состояние.  
• Зависит от: IAM (аутентификация), все сервисы блоков 1, 2, 3.
**Компонент П.3. Внутреннее API (Internal API)**  
• Что делает: API для взаимодействия между микросервисами платформы. Обеспечивает единую точку доступа и observability.  
• Границы: доступно только внутри платформы. Не публичное.  
• Зависит от: все сервисы (как потребитель и как провайдер).
**Компонент П.4. Статусная страница**  
• Что делает: публичная страница о доступности сервисов. Отображает текущие инциденты, плановые работы, историю доступности.  
• Границы: только отображение. Не управляет инцидентами.  
• Зависит от: компонент 3.4 (Управление инцидентами).

## Блок 1. Управление услугами (OSS/Service Control Plane)
Задача блока - технически предоставить пользователям сервисы/ресурсы исходя из предусловий (наличие/отсутствие необходимых доступов/квот)
**Компонент 1.1. Учёт клиентов и доступ (IAM)**  
• Что делает: хранит пользователей, группы, сервисные аккаунты. Управляет аутентификацией (кто) и авторизацией (что можно). Проверяет доступ к проектам и права на действия.  
• Границы: не знает про квоты, не знает про деньги, не хранит ресурсы. Только идентификация и разрешения.  
• Зависит от: компонент 1.3 (Resource Manager) для проверки существования проекта.
**Компонент 1.2. Управление проектами (Tenant Management)**  
• Что делает: управляет жизненным циклом проектов/тенантов: создание, блокировка (при долгах), удаление. Обеспечивает изоляцию между проектами.  
• Границы: не хранит ресурсы внутри проекта. Не управляет доступом (это IAM). Только оболочка проекта.  
• Зависит от: компонент 1.3 (Resource Manager), компонент 2.4 (Billing) для блокировки при долгах.
**Компонент 1.3. Инвентаризация ресурсов (Resource Manager)**  
• Что делает: единый источник правды о всех ресурсах платформы: VM, кластеры, диски, сети, бэкапы. Хранит состояние, отношения, теги, метаданные.  
• Границы: не хранит метрики потребления (CPU сейчас). Не знает тарифы. Только факт существования и атрибуты.  
• Зависит от: компонент 1.7 (Orchestration Engine) получает события создания/удаления, компонент 1.1 (IAM) для проверки доступа к ресурсам.
**Компонент 1.4. Каталог услуг (Service Catalog)**  
• Что делает: хранит описание всех услуг: VM, K8s, Backup, S3. Для каждой услуги: параметры, допустимые действия, привязка к тарифам, ограничения. Проверяет доступность услуги для проекта.  
• Границы: не знает про квоты и лимиты. Не хранит состояние ресурсов. Только мета-информация об услугах.  
• Зависит от: компонент 1.2 (Tenant Management) чтобы знать, какие услуги включены проекту.
**Компонент 1.5. Квоты и лимиты (Quota Engine)**  
• Что делает: хранит лимиты по проектам: максимум vCPU, RAM, дисков, количества ресурсов. Проверяет при создании, не превышен ли лимит.  
• Границы: не знает про деньги. Не знает про доступ. Только числа и лимиты.  
• Зависит от: компонент 1.3 (Resource Manager) для получения текущего потребления, компонент 1.2 (Tenant Management) для привязки к проекту.
**Компонент 1.6. Управление жизненным циклом услуги (Service Lifecycle Manager)**  
• Что делает: управляет состояниями услуги: активна, приостановлена, удалена, в ошибке. Обрабатывает сложные переходы (пауза → возобновление).  
• Границы: часть Orchestration Engine или отдельный слой над ним. Не работает напрямую с провайдерами.  
• Зависит от: компонент 1.7 (Orchestration Engine), компонент 1.3 (Resource Manager), компонент 2.4 (Billing) при паузе.
**Компонент 1.7. Оркестратор выполнения (Orchestration Engine)**  
• Что делает: единый движок workflow для всех операций: создать, изменить, удалить, приостановить. Управляет последовательностью шагов, повторами, откатами. Не знает, как именно создать VM — вызывает провайдеров.  
• Границы: не содержит логики конкретных технологий. Только координация.  
• Зависит от: все провайдеры (компонент 1.9), компонент 1.3 (Resource Manager) для обновления статуса, компонент 3.7 (Audit), компонент 3.8 (Notifications).
**Компонент 1.8. Федерация IAM (Federation IAM)**  
• Что делает: обеспечивает связь между IAM в on-prem инсталляции и центральным IAM в public. Единый вход (SSO) для гибридных сценариев.  
• Границы: только синхронизация идентификации. Не хранит политики доступа (они в каждом IAM свои).  
• Зависит от: компонент 1.1 (IAM) оба конца.
**Компонент 1.9. Исполнители (Providers/Driver)**  
• Что делает: набор драйверов для конкретных технологий: OpenNebula Provider, Боцман Provider, S3 Provider, Backup Provider. Реализуют интерфейс «создать/удалить/обновить» для своего типа ресурса.  
• Границы: не знают про бизнес-логику, клиентов, квоты. Только техническое исполнение.  • Зависит от: внешние API (OpenNebula, Боцман и т.д.).
**Компонент 1.10. Гибридная консоль (Hybrid Console Logic)**  
• Что делает: бэкенд для единой панели управления гибридом. Агрегирует данные из Resource Manager on-prem и public, отдаёт единый view.  
• Границы: только чтение и агрегация. Не управляет ресурсами напрямую.  
• Зависит от: компонент 1.3 (Resource Manager) обе инсталляции, компонент 1.8 (Federation IAM).

## Блок 2. Коммерция (Commerce Plane)
Задача блока - монетизировать предоставляемые сервисы/услуги, корректно их обсчитав в сторону пользователя
**Компонент 2.1. Управление клиентами (CRM / Customer Management)**  
• Что делает: хранит данные о клиентах: юридические лица, контакты, договоры, платёжные реквизиты. Управляет статусом клиента (активен, заблокирован).  
• Границы: не знает про ресурсы и потребление. Только информация о клиенте.  
• Зависит от: компонент 1.2 (Tenant Management) для связи клиент → проекты.
**Компонент 2.2. Тарифы и ценообразование (Pricing)**  
• Что делает: хранит тарифные правила: почасовая оплата, фиксированная плата, промокоды, скидки, пакеты услуг. Отвечает на вопрос «сколько стоит ресурс X в проекте Y».  
• Границы: не знает, сколько потребил конкретный ресурс. Только правила расчёта.  
• Зависит от: компонент 1.4 (Service Catalog) для привязки тарифов к услугам.
**Компонент 2.3. Учёт потребления (Usage)**  
• Что делает: собирает метрики потребления от провайдеров и мониторинга. Агрегирует в единицы для биллинга: CPU-часы, GB-часы, количество запросов. Передаёт агрегаты в Billing.  
• Границы: не хранит тарифы. Не списывает деньги. Только учёт потребления.  
• Зависит от: компонент 1.3 (Resource Manager) чтобы понять, какому проекту принадлежит ресурс, компонент 3.1 (Platform Observability) как источник метрик.
**Компонент 2.4. Биллинг и расчёты (Billing )**  
• Что делает: получает агрегированное потребление от Metering, применяет тарифы из Tariff & Pricing, списывает с баланса или выставляет счёт. Управляет холдированием, начислениями, платежами.  
• Границы: не хранит метрики потребления. Не знает, как устроена услуга внутри.  
• Зависит от: компонент 2.3 (Metering), компонент 2.2 (Tariff & Pricing), компонент 2.1 (CRM) для реквизитов, компонент 3.7 (Audit).
**Компонент 2.5. Лицензирование (Licensing)**  
• Что делает: управляет лицензиями для on-prem поставок: генерация ключей, проверка при активации, ограничение по количеству сокетов/ВМ/пользователей.  
• Границы: не участвует в public-биллинге. Только для on-prem.  
• Зависит от: компонент 2.1 (CRM) кому выдана лицензия, компонент 1.7 (Orchestration Engine) для проверки при создании.
**Компонент 2.6. Аналитика и отчёты (Analytics & Dashboards)**  
• Что делает: готовит отчёты для клиентов (детализация расходов, прогнозы) и для внутренних команд (выручка, маржинальность, тренды).  
• Границы: только чтение данных из других сервисов. Не влияет на операции.  
• Зависит от: компонент 2.3 (Metering), компонент 2.4 (Billing), компонент 2.1 (CRM), компонент 1.3 (Resource Manager).

## Блок 3. Надёжность (Reliability Plane)
Задача блока - обеспечивать стабильность, наблюдаемость и соответствие SLA. Быстро обнаруживать проблемы и реагировать на них.
**Компонент 3.1. Наблюдаемость платформы (Platform Observability)**  
• Что делает: собирает метрики, логи, трейсы со всех компонент платформы. Хранит, индексирует, визуализирует для SRE и инженеров.  
• Границы: только сбор и хранение. Не анализирует и не алертит (это Alerting).  
• Зависит от: все компоненты платформы как источники данных.
**Компонент 3.2. Наблюдаемость для клиента (Customer Observability)**  
• Что делает: предоставляет клиенту метрики и логи его ресурсов с фильтрацией по tenant. Отдаёт через API и UI.  
• Границы: не показывает данные других клиентов. Не даёт доступа к платформенным метрикам.  
• Зависит от: компонент 3.1 (Platform Observability) как источник, компонент 1.1 (IAM) для фильтрации.
**Компонент 3.3. Алертинг (Alerting)**  
• Что делает: анализирует метрики и логи по правилам. При превышении порогов отправляет алерты в Incident Management или дежурным.  
• Границы: только генерация алертов. Не управляет людьми и эскалацией.  
• Зависит от: компонент 3.1 (Platform Observability).
**Компонент 3.4. Управление инцидентами (Incident Management)**  
• Что делает: получает алерты, группирует в инциденты, определяет приоритет и масштаб. Управляет эскалацией, ведёт таймеры (время до реакции, до восстановления). Фиксирует хронологию.  
• Границы: не исправляет проблему. Только координирует процесс.  
• Зависит от: компонент 3.3 (Alerting), компонент 1.3 (Resource Manager) чтобы понять, кого затронуло, компонент 3.8 (Notifications).
**Компонент 3.5. Расчёт SLA (SLA Engine)**  
• Что делает: рассчитывает фактическую доступность услуг для каждого клиента. Сравнивает с обещанным SLA из договора. Определяет, было ли нарушение.  
• Границы: не выплачивает компенсации. Только расчёт.  
• Зависит от: компонент 3.4 (Incident Management) для времени простоя, компонент 1.3 (Resource Manager) для информации о ресурсах клиента, компонент 2.1 (CRM) для SLA из договора.
**Компонент 3.6. Компенсации (Compensation Engine)**  
• Что делает: при нарушении SLA автоматически рассчитывает размер компенсации (кредиты, скидки). Передаёт команду в Billing на начисление.  
• Границы: не управляет деньгами напрямую. Только передаёт распоряжение.  
• Зависит от: компонент 3.5 (SLA Engine), компонент 2.4 (Billing), компонент 2.1 (CRM).
**Компонент 3.7. Аудит (Audit)**  
• Что делает: логирует все значимые действия: кто, когда, что сделал, с каким ресурсом, успешно или нет. Хранит в неизменяемом виде.  
• Границы: не влияет на операцию. Только запись.  
• Зависит от: все компоненты вызывают при действиях.
**Компонент 3.8. Уведомления (Notifications)**  
• Что делает: отправляет уведомления клиентам (email, SMS, webhook) и дежурным (телеграм, PagerDuty) о событиях: создание ресурса, инцидент, плановые работы.  
• Границы: только доставка сообщений. Не формирует содержание (получает готовое).  
• Зависит от: компонент 1.7 (Orchestration Engine), компонент 3.4 (Incident Management), компонент 2.1 (CRM) для контактов.
**Компонент 3.9. Системный бэкап (Platform Backup)**  
• Что делает: регулярно создаёт бэкапы состояния платформы: базы данных, конфигурации, метаданные. Обеспечивает восстановление после катастроф.  
• Границы: не касается клиентских данных. Только состояние самой платформы.  
• Зависит от: компонент 1.3 (Resource Manager), компонент 1.1 (IAM), компонент 2.4 (Billing) как источники данных для бэкапа.

## Блок 4. Развитие (Ecosystem Plane) — уровень зрелости 4
Задача блока - расширять платформу за счёт мульти-облака, инструментов для разработчиков и партнёрской экосистемы.
**Компонент 4.1. Мульти-облачные адаптеры (Multi-cloud Adapters)**  
• Что делает: адаптеры к API других облаков (AWS, Azure, Yandex). Позволяют управлять чужими ресурсами через единый API платформы.  
• Границы: только трансляция вызовов. Не хранит состояние чужих ресурсов (или хранит минимально).  
• Зависит от: компонент 1.7 (Orchestration Engine), внешние API облаков.
**Компонент 4.2. Платформа для разработчиков (DevPlatform)**  
• Что делает: инструменты для разработчиков: CI/CD, шаблоны приложений, тестовые среды, интеграция с Git.  
• Границы: надстройка над основными сервисами. Не заменяет IaaS/PaaS.  
• Зависит от: компонент 1.1 (IAM), компонент 1.3 (Resource Manager), компонент 1.7 (Orchestration Engine).
**Компонент 4.3. Маркетплейс (Marketplace)**  
• Что делает: витрина решений от партнёров и собственных SaaS-приложений. Подключение в один клик, учёт потребления.  
• Границы: не управляет базовыми IaaS-услугами. Только дополнительный слой.  
• Зависит от: компонент 1.4 (Service Catalog), компонент 2.4 (Billing), компонент 2.6 (Partner Marketplace) если отдельно.
**Компонент 4.4. Соответствие требованиям (Compliance & Certifications)**  
• Что делает: готовит отчётность по требованиям регуляторов (ГОСТ, 152-ФЗ, PCI DSS). Хранит доказательную базу для аудитов.  
• Границы: только отчётность. Не влияет на безопасность напрямую.  
• Зависит от: компонент 3.7 (Audit), компонент 1.1 (IAM), компонент 1.3 (Resource Manager).

## Границы между компонентами (ответ на п. 4)

Чтобы соблюдался платформенный подход, нужно жёстко зафиксировать правило:

**Компонента не может выполнять работу, которая относится к другой компоненте, даже если «так проще»**

Примеры нарушений и правильных границ:

❌ Оркестратор сам считает потребление и пишет в биллинг.  
Правильно: Оркестратор создал ресурс, отдал событие в шину, Учёт потребления подхватил и начал собирать метрики.

❌ Биллинг сам проверяет, есть ли у клиента доступ к услуге.  
Правильно: Биллинг говорит «клиент заблокирован», IAM проверяет доступ и блокирует API.

❌ Система инцидентов сама пишет в чат клиенту.  
Правильно: Система инцидентов передаёт статус в Коммуникации, те отправляют уведомление.
