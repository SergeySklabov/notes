## 1\. Введение

*Тенант —* это логически изолированная единица, представляющая отдельного клиента, организацию, проект или команду, которая использует ресурсы облачной платформы.

*Tenant Manager System (TMS)* —компонент мультитенантной облачной платформы, ответственный за логику управления жизненным циклом тенанта, отвечает за изоляцию, конфигурирование и администрирование тенантов

- Хранит и управляет иерархией тенантов
	- например: *Организация →тенант ->ресурсы*
- Управление жизненным циклом организаций (клиентов) и тенантов внутри организаций — создание, модификация, приостановка (активация/деактивация), удаление. При этом Tenant Manager несет ответственность за создание записи и присвоение идентификатора организации и создаваемому тенанту. Все взаимодействия Tenant Manager с оркестраторами выполняется через асинхронную шину сообщений. Оркестраторы самостоятельно проверяют, что суммарный объем уже выделенных ресурсов вместе с новым запросом не превышает выделенную квоту. Если квота превышена, оркестратор отклоняет запрос и возвращает ошибку. Tenant Manager делегирует создание ресурсов специализированным оркестраторам:
	- Orchestrator IaaS — создание и удаление виртуальных машин;
		- Orchestrator SDN — создание и удаление виртуальных сетей;
		- Orchestrator SDS — создание и удаление виртуальных дисков и хранилищ.
- Проеряет права пользователя на создание ресурсов в конкретном тенанте
- Сохраняет данные аудита
- предоставление API и (и UI как часть GUI фронтов);
- Orchestrator Manager (возможно возникнет необходимость в таком компоненте TBD) может собирать комплексные запросы на наборы ресурсов, например, для XaaS может потребоваться одновременное выделение ВМ, сетей, дисков. Для проверки возможности размещения ресурсов одновременно Orchestrator Manager формирует запрос на проверку в каждый оркестратор и суммирует результат. Также этот компонент должен нести ответственность за своевременное удаление (или изменение статуса) неиспользуемых ресурсов в ситуациях, когда по какой-то причине не удалось освободить ресурсы при изменении статуса тенанта.
- TM не хранит пользователей и их роли, не хранит привязки пользователей к тенантам (это IAM), однако хранит "типы ролей"
- TM не управляет ресурсами напрямую, он использует для этого Оркестраторы.
- TM не ведет контроль квот и лимитов ресурсов для тенантов и виртуальных дата-центров (VDC). Предполагается, что источник правды о квотах это *QuotaManager* т.к значение квоты может быть изменено какой-то внутренней бизнес-логикой соответствующего компонента (сейчас это BillManager). QuotaManager запрашивается оркестраторами на предмет актуальных лимитов соответствующих ресурсов.
- TM не считает деньги и не выставляет счета

## 1.1. Цели TMS

- обеспечить автоматизацию жизненного цикла тенантов при создании, активации, деактивации и удалении тенантов, предоставить единый API;
- обеспечение мультитенантной изоляции, гарантировать, что данные одного тенанта недоступны другим тенантам;

## 1.2. Задачи TMS

1. Операции CRUD для тенанта (с пердоставлением API):
	1. создание нового тенанта, валидация данных, генерация уникального идентификатора, создание записи в БД, инициализация изолированного пространства.
		2. чтение и пердоставление информации о тенантах
		3. изменение информации о тенанте
		4. удаление тенанта и инициализация освобождения ресурсов
2. Ведение БД тенантов с их атрибутами (название, владелец, метаданные).
3. Управление состоянием тенантов: active, suspended, disabled, deleted. Обработка переходов между состояниями с каскадным оповещением связанных сервисов (менеджеров/оркестраторов ресурсов).
4. Интеграцияс IAM, привязка тенантов к пользователям/ролям/политикам. Разграничение доступа: администратор платформы (организации) видит все тенанты, пользователь — только свои.
5. Интеграция с биллингом для передачи событий создания/изменения тенанта в платежную систему.
6. Аудит и логирование – фиксация всех действий над тенантами в неизменяемом audit log.

## 1.3. Свойства TMS

- Централизованность – TMS является единственным источником правды (single source of truth) для информации о тенантах. Изменение состояние тенантов проходит через TMS, что исключает рассинхронизацию между компонентами.
- Масштабируемость – архитектура TMS должна горизонтально масштабироваться для поддержки тысяч и миллионов тенантов.
- Отказоустойчивость - TMS должен быть спроектирован с учетом репликации данных и резервирования потоков управления. Если произошел сбой, то потеря TMS означает невозможность изменения и создания новых тенантов, но не влияет на работу уже запущенных (они продолжают функционировать автономно).
- Идемпотентность операций – операции создания/изменения тенантов должны быть идемпотентными. Повторный запрос с тем же идентификатором не должен приводить к дублированию тенанта или ошибочному состоянию.
- Асинхронность и событийно-ориентированная архитектура. Реализуется за счет асинхронных вызовов или публикации/подписки на события в очередь.
- Расширяемость (изменяемость) -TMS должен поддерживать плагины для интеграции с различными оркестраторами ресурсов.

Безопасность API TMS защищены аутентификацией и авторизацией. Данные тенантов шифруются как at-rest, так и in-transit. В совокупности с менеджером квот реализуют защиту от "шумных соседей"

## 2\. Монетизация

TMS монетизируется не как отдельный компонент, а как платформенный слой, без которого мультитенантная облачная инфраструктура не может масштабироваться. TMS дает возможность привнести новый тип транзакций и артефактов за которые можно взимать плату.

## 2.1. Целевая Аудитория

- Коропративные клиенты, те, что строят свое приватное облако
- Госсектор (B2G), важен онпремис и соответствие регуляриторике
- Партнеры-провайдеры, которым необходима кастомизация TMS под свою специфику или использование в пердопределенных конфигурациях (например, телеком).

## 2.2. Модели монетизации

TMS как компонент облачной платформы может монетизироваться по следующим моделям:

1. как часть платформы, когда стоимость TMS включена в стоимость инфраструктуры
	1. стоимость платформы и обслуживания включает стоимость компонента TMS и его поддержки (единоразовая покупка)
		2. годовая подписка на использование TMS с получением обновлений и поддержкой
		3. стоимость платформы включает стоимость компоеннта TMS, стоимость поддержки TMS выставляется отдельно по факту возникновения инцедента
		4. дополнительная стоимость формируется за счет границ потребления, например, в базовый пакет входит 5 изолированных тенантов внутри одной организации, в случае первышения лимита, дополнительные тенанты и связь между ними оплачиваются отдельно по тарифу. Может быть градация по пакетам – 5, 20, 200, 1000 управляемых тенантов.
		5. pay-as-u-go оплата за использование активного тенанта
		6. плата за количество (лимиты) использования API (API экономика)
		7. конфигурации для географически распределенных тенантов могут тарифицироваться особо
		8. плата за лицензию, покрывающую конфигурацию гибридного облака (on prem + public)
		9. в случае мультиоблака TMS может быть центральным хабом транзакций, плата за кросс-облачные операции
		10. лата за объем аудит-логов и/или количество записей (объъем БД и стораджа)
		11. плата за аналитику метрик и паттернов доступа, предоставление отчетности, выявление аномалий, нотификации
2. при интеграции со сторонними компонентами/сервисами
	1. плата за экспорт в стороннюю SIEM систему
		2. плата за экспорт в стороннюю BI/аудит систему

## 2.3. Каналы продаж

- Прямые enterprise-продажи (Field Sales) — аккаунт-менеджеры
- Дистрибьюторы ПО, которые осуществляют продажи ACP
- Интеграторы, занимающиеся трансофрмацией ИТ ландшафта, переходом в облако
- Участие в государственных тендерах

## 3\. Архитектурные принципы

Основные архитектурные принципы построения TMS компонента:

- TMS – "единый источник правды" о тенантах в платформе. Ни один другой сервис не хранит собственное состояние тенантов.
	- Все операции создания/изменения/удаления тенантов проходят через TMS API (API Gateway)
		- TMS владеет Tenant БД
		- Остальные сервисы (IAM, биллинг, оркестраторы) получают данные через события (или асинхронные вызовы)
- Асинхронность. TMS публикует события в очередь (шину), а специализированные воркеры подписываются на них и выполняют фактическую работу. Посредством такого подхода осуществляется:
	- разделение ответственности (Separation of Concerns)
		- возможность перезапука обработки события при сбоях
		- горизонтальное масштабирование воркеров независимо от TMS
		- не блокируеся API-слой при тяжелых операциях (например, создание ВМ Брестом)
- Идемпотентность. Все операции TMS должны быть идемпотентными. Повторный запрос с тем же идентификатором не должен приводить к дублированию тенанта или ошибочному состоянию.
- Изолированность (может быть реализована комплексом компонентов платформы. TMS поддерживает логику.)
	- Изолированность данных. TMS должна обеспечивать изоляцию данных разных клиентов платформы. Стратегии изоляции:  
		- Отдельная физическая СХД/диск для каждого тенанта.
				- Отдельная БД для каждого тенанта
				- Отдельная схема в общей БД Enterprise, когда важен баланс изоляции и стоимости
				- Отдельные правила Row-Level Security (RLS) для общей таблицы
				- Уровень изоляции определяется тарифом и настраивается администратором платформы для каждого тенанта или группы тенантов.
		- Изолированность CPU/compute.
		- Изолированность сети.
- Расширяемость (изменяемость). Возможность использования плагинов. В нашем случае важна овзможность расширять количество оркестраторов (менеджеров ресурсов)
- Поддержка мультитенантности и мультиорга
- REST API для операций по управлению состояниями тенантов (CRUD)
- Высокая доступность (HA) и восстанавливаемость
- TMS должен иметь возможность расширения методов проверки за счет подключения новых или сторонних модулейб
- Наблюдаемость и аудит (с алертингом) с возможностью детектирования аномалий. Логи и метрики хранятся read-only.
- Безопасность (шифрование, контроль доступа, аудит)

## 4.2. Пользователи-компоненты платформы

*Orchestrator*

- Компонент, отвечающий за управление определенным ресурсом в привязке к тенантам (CRUD), отслеживает и меняет состояние ресурса.
- При запросе на размещение ресурса, Оркестратор запрашивает у *QuotaManager* квоту ресурса для текущего тенанта, сравнивает с текущим расходом, и принимает решение о размещении ресурса (ВМ, сеть, диск итп) или возвращает ошибку.
- Оркестратор может делать оценку выполнимости запроса на размещение ресурса не выполняя его (по API). Проверяется размер квоты и сравнивается с суммой объема размещенного ресурса и запрашиваемого, результат возвращается. При этом для избежания гонок ресурс может быть предварительно забронирован оркестратором (опция интерфейса).
- Оркестратор сообщает об изменении статуса ресурса нотифицируя подписчиков через шину сообщений

*Quota Manager*

- компонент для управления квотами для организации/тенанта/VDC. Квотации привязываются к организации или тенанту, привязывает лимиты к ресурсам.
- При изменениии значения квоты, Quota Manager нотифицирует Tenant Manager*.*
- Billing Service может управлять величиной квоты через Quota Manager (например, при назначении тарифа на тенант, одновременно назначаются квоты на ресурсы тенанта)
- величина квоты запрашивается Tenant Manager у Quota Manager до обращения в оркестратор.
- Quota Manager должен сообщать в Tenant Manager о необходимости изменения статуса тенанта или конкретного ресурса. Tenant Manager по получении информации о необходимости изменения статуса тенанта, посредством оркестраторов, меняет статус у соответствующих ресурсов и модифицирует запись о тенанте.

см. также [Управление квотами](https://aic.astra.ru/adm_guide/brest/ruk_admin_2/4_vm_units_management/4.5_quota_management.html) пример [JSON c информацией о квотах для VDC](https://life.astralinux.ru/download/attachments/612884042/VDC_quota.json?api=v2) от BillManager

*Blling Service*

- привязывает тарифы к организации или тенанту, привязывет стоимости к ресурсам.
- может выставлять и модифицировать квоты.
- Опрашивает Оркестраторы на предмет объема расхода ресурсов. В случае полного расхода оплаченного (зарезервированного) ресурса, модифицирует квоту таким образом, чтобы инициировать смену статуса тенанта Тенант Менеджером.
- Выставление счетов и учет затрат (отдельный интерфейс комопнента)

*Message Bus*

- шина для обмена асинхронными сообщениями, реализующая модель публикации-подписки
- Используется для обмена сообщениями между Tenant Manager и Оркестраторами

*Опции для реализации:*

- для абсолютной изоляции на уровне организаций или тенантов, могут быть использованы отдельные экземпляры IAM для каждой организации (и, соответственно, ALD как источника знаний о пользователях)
- для физической изоляции хостов разных организаций/тенантов следует использовать affinity rules (настройка средствами Бреста)

## 5\. Реализация компонента TMS

## 5.1. Принцип реализации компонента

Эвалюционный подход предполагает создание архитектуры платформы включающуей централизованный TMS, создание компонента TMS, оркестраторов ресурсов, менеджера квот и интеграцию их с существующими компонентами: ПК СВ Берст, Астра Мониторинг, SDS, SDN. APIM, BillManager, платформой XaaS, IAM. В адльнейшем планируется наращивание функциональных возможности TMS и выделение редакций для обеспечения специфики поставок.

*Ключевые положения*

- Подсистема TMS выделяется в самостоятельный архитектурный компонент, который обладает четко определенным API:
	- Приватный (интеграция с платформенными и функциональными сервисами)
		- Административный (интеграция с Порталом Администратора)
- Подсистемы и сервисы облачной платформы интегрируются с подсистемой TMS через стандартизированные интерфейсы и протоколы (очередь сообщений);
- Внутренняя реализация подсистемы TMS не раскрывается конечным сервисам — они взаимодействуют только через API подсистемыTMS;
- Ролевая модель управления доступом (RBAC), структура пользователей, ролей и тенантов формируется и управляется исключительно в подсистеме IAM.

Подсистема TMS должна обеспечивать:

| Идентификация  Аутентификация  Авторизация | - Проверка аутентичности пользователей или устройств, гарантируя, что они являются теми, за кого себя выдают. - Управление доступом на основе ролей (RBAC): назначает разрешения на основе предопределенных ролей пользователей; - Управление доступом на основе атрибутов (ABAC): оценивает атрибуты (например, должностные обязанности, местоположение или тип устройства) для предоставления доступа. |
| --- | --- |
| Изоляция тенантов | Обеспечение изоляции тенантов за счет разделения доступа (посредством соответствующих оркестраторов) |
| Управление состоянием тенантов | Управление состоянием тенантов посредством создания соответсствующих записей в БД, публикацией сообщений в очередь и обработкой сообщений из очереди |
| API | Изолированные REST API для межсервисного и административного взаимодействия — изоляция функций управления на уровне платформы и отдельных тенантов |
| Управление тенантами для федеративной конфигурации платформы | TBD |
| Аудит | Генерация записей об измеенниях состояния тенантов. |
| Хранение информации о тенантах (организациях) | Хранение и организация информации о тенанте (организации) в защищенном формате. |

*Архитектурная реализация*

- Подсистема TMS реализует REST API, которые соответствуют требованиям облачной платформы;
- Внутри подсистемы TMS используется хранилище данных в качестве поставщика информации о тенантах;
- Данные о тенантах доступны в подсистемеTMS, но управление осуществляется централизованно через API или специализированный интерфейс;
- Возможна федеративная конфигурация;
- Интеграция комопнентов платформы с подсистемой TMS происходит через асинхроннй интерфес;

*Безопасность*

- Все вызовы к подсистеме TMS защищены теми же механизмами аутентификации и авторизации, что предоставляются в интересах других сервисов;
- Предусмотрена поддержка SSO и MFA, а также внешних провайдеров аутентификации для порталов администратора платформы и авдимнистратора тенанта;
- Реализуется генерация логирования и событий аудита всех операций с доступом и их отправка в централизованный сервис.

*Масштабируемость*

- Архитектура предусматривает горизонтальное масштабирование подсистемы TMS и распределение нагрузки;
- (В перспективе) Архитектура предусматривает мультизональное и мультирегиональное масштабирование;
- Добавление новых функциональных сервисов требует только конфигурации в подсистемеTMS, без модификации их внутренней логики;

## 6\. Метрики

*Бизнес (выручка)*

- сумма выручки по отдельным моделям продажи
- количество приходящих и удерживаемых клиентов по отдельным моделям продажи и поставки
- соблюдение SLA
- общая аудитория системы (GAGR)

*Бизнес (клиенты)*

- процент тенантов, удалённых или приостановленных за период
- количество ресурсов (ВМ, сети, диски, пользователи) на один тенант
- операционные затраты на поддержку одного тенанта (инфра + поддержка)
- процент тенантов, созданных через: портал самообслуживания; через API; администратором

*Продукт*

- общее количество обслуживаемых тенантов
- время от запроса на создание тенанта до его готовности
- процент запросов на создание тенанта, завершившихся успешно
- время от запроса на удаление тенанта до освобождения всех связанных с ним ресурсов
- процент (объем) "висящих ресурсов" – те, что не освобождены после приостановки или удаления тенанта
- прохождение аудитов безопасности (количество и % успешных за период)
- количество подсистем (приложений, рост количества) использующих TMS
- количество ошибок, инцидентов
- покрытие потребностей рынка в части поддержки популярных технологий и функций
- поддержка количества внешних интеграций (SEIM,BI)
- быстрота восстановления после сбоя (% доступности)
- задержки выполнения TMS API
- % соответствие требованиям регулятора и ИБ

*Разработка*

- оценка простоты (количество ресурсов, времени) на интеграцию нового компонента с TMS
- сложность внесения изменений (длительность, ресурсоемкость. необходимость специфичной экспертизы)
- % ошибок в коде

*Обслуживание*

- быстрота выполнения заявок и разрешения инцидентов
- объем привлеченного обсулуживания, количество контрактов на обслуживание
- вытеснение конкурентных решений за счет pre-sale и GoTo Market решений (по платформе)

## 7\. Примеры сквозных сценариев.

## 7.1. Сценарии для администратора платформы

Администратор платформы управляет всей платформой: создаёт тенанты, управляет глобальными настройками.

Сценарий 1:

1. Администратор платформы заполняет форму: название организации, регион, подразделение
2. TMS:  
	1. \- создает уникальный идентификатор тенанта
		2. \- создает запись тенанта в БД (статус PENDING)
		3. \- опционально вызывает IAM для создания администратора тенанта
		4. \- Вызывает Billing и создает экземпляр тарифного плана (должен быть доступен набор базовых тарифных планов, которые могут кастомизироваться позднее)
		5. \- Вызывает SDN, создает изолированную сеть для тенанта
		6. \- опционально вызывает настройку DNS для создания записи домена тенанта <org>.<tenantID>.ru
		7. \- TMS обновляет статус на ACTIVE
3. Администратор платформы получает подтверждение: tenant ID, root credentials, URL входа

Сценарий 2:

1. Администратор платформы выбирает тенант и действие Suspend (например, за неуплату)
2. TMS проверяет: не в SUSPENDED ли уже
3. TMS обновляет статус на SUSPENDED
4. TMS отправляет события:  
	1. в API Gateway блокировать все запросы к API тенанта
		2. в оркестраторы ресурсов -- приостановить или освободить ресурсы
5. Администратор тенанта нотифицируется об изменении состояния тенанта

Сценарий 3:

1. Администратор платформы выбирает тенант и действие Delete
2. TMS запускает компенсирующую сагу:
3. выкладывает в шину сообщений сообщение <tenatnID>.deleting
4. в оркестраторы ресурсов получая это сообщение начинают особождать ресурсы
5. IAM: помечает на удаление пользователей тенанта (или поля, связанные с тенантом)
6. Billing закрывает подписку и выставляет финальный счёт
7. DNS: удаляет DNS-запись
8. TMS помечает тенант как deleted
9. Администратор платформы: тенант исчезает из списка активных
10. Через определенный период система вычищает все помеченные на удаление записи
11. Система производит сборку мусора для выявления висящих ресурсов

Сценарий 4:

1. Администратор платформы открывает дашборд <tmshome>/tenants
2. TMS возвращает список тенантов со статусами и дополнительной информацией
3. Администратор платформы видит метрики
