# ACP Platform — AGENTS.md

> **Astra Cloud Platform (ACP)** — комплексное решение, на базе которого клиентам ГК Астры предоставляются облачные продукты. Платформа предоставляет стандартизированные и гибкие возможности для запуска и эксплуатации сервисов на общем платформенном слое, избавляя от необходимости продумывать взаимодействие с инфраструктурой (VM, K8s) и общими сервисами (IAM, Billing, Security, Audit) — всё это предоставляется через централизованные механики платформы.
>
> **Источник:** [[Astra/Astra Cloud Platform/Видение платформы]], [[Astra Cloud Platform Product Vision (ACP) v0.9 — Сергей Склабовский]]

## 0. Специфика ACP

### 📐 Определение платформы

ACP — это единое ядро для масштабируемого и управляемого предоставления облачных продуктов конечным клиентам. Ключевые цели:

- **Монетизация** виртуальных ресурсов через 4 модели поставки: public, on-prem, hybrid, multi-cloud
- **Фундаментальные сервисы** — IAM, Monitoring, Logging, Audit, Resource Manager — общее основание для всех продуктов, исключающее дублирование
- **Самообслуживание** — клиенты самостоятельно управляют ресурсами через портал и API
- **Технологическая независимость** — смена провайдеров (OpenNebula, Боцман и др.) без изменения клиентского API
- **Сокращение time-to-market** для новых продуктов через готовые интеграции и переиспользуемые шаблоны

### 🧱 Функциональные блоки (из видения)

| Блок | Описание | Компоненты |
|------|----------|------------|
| **Пользовательский слой** | Точки входа: UI, Public API, Internal API | Личный кабинет, API Gateway (external/internal), Status page |
| **Блок 1. Service Control Plane** | Управление услугами и ресурсами | IAM, Tenant Management, Resource Manager, Service Catalog, Quota Engine, Orchestration Engine, Federation IAM, Providers/Drivers |
| **Блок 2. Commerce Plane** | Монетизация услуг | CRM, Pricing, Usage, Billing, Licensing, Analytics |
| **Блок 3. Reliability Plane** | Стабильность и наблюдаемость | Platform Observability, Customer Observability, Alerting, Incident Management, SLA Engine, Audit, Notifications, Platform Backup |
| **Блок 4. Ecosystem Plane** | Развитие и экосистема | Multi-cloud Adapters, DevPlatform, Marketplace, Compliance |

> **Важно:** Компоненты не должны выполнять работу друг друга. Каждая компонента делает ровно одну вещь и делегирует смежные задачи соседям через шину событий.

### 🏗️ Ключевые архитектурные принципы ACP

- **API стандарт:** RESTful JSON, единый API Style Guide (RFC 2119, RFC 3986, RFC 9110)
- **Пагинация:** Offset-based (page/page_size)
- **Асинхронные операции:** Операционно-ориентированный подход (202 + Operation) для долгих операций (>1 мин)
- **Формат данных:** snake_case атрибуты, camelCase на фронте (трансформер)
- **HTTP-методы:** POST (создание), GET (чтение), PATCH (частичное обновление), PUT (замена), DELETE (удаление)
- **Идемпотентность:** POST — нет, GET/PUT/DELETE — да
- **Платформенный контекст:** Security Context (AuthN/Identity/AuthZ) + Tenant Context + Execution Context в каждом запросе
- **Аутентификация:** OAuth 2.0 / OIDC (Authorization Code Flow + Client Credentials)
- **Формат токена:** JWT (первая итерация), opaque-токены (позже)
- **Архитектура фронта:** BFF (Backend for Frontend) через API Gateway — публичный (клиент) и приватный (админ)
- **Доставка:** Два портала — самообслуживания (внешний) и администрирования (внутренний)
- **Модульная поставка:** возможность получить только необходимый набор функций с последующим расширением

### 🎯 Ключевые свойства

- Платформа ориентирована на **ресурсы** (ВМ, диски, сети, образы), а не на услуги
- Self-service для клиентов: создание ресурсов без обращения к оператору
- Измеряемый сервис (metered): учёт потребления для биллинга и аналитики
- Multi-tenancy: изоляция клиентов, квоты, ролевая модель
- Наблюдаемость: метрики, логи, трассировка, алертинг
- Соответствие NIST: 5 обязательных характеристик облака
- **MVP = релиз ACP 2.2.0** (ноябрь 2026): IaaS (ВМ, диски, сети, образы) + SSO + SDN + портал самообслуживания

## 2. Роли AI-агентов

### Atlas (Master Orchestrator)
- **Оркестрация** — координация всех агентов
- **Верификация** — проверка результатов после каждого шага
- **Никогда не пишет код** — только читает, верифицирует, оркестрирует
- Вход: todo-лист, распределяет, верифицирует, двигает дальше

### Oracle
- **Архитектурный консультант**
- Когда звать: сложные архитектурные вопросы, ADR, конфликты (Пронюшкин vs Шадрин)
- Режим: read-only, анализирует документацию, даёт рекомендации
- Не пишет код, не правит файлы

### Librarian
- **Исследователь** — поиск документации, API-спецификаций, внешних источников
- Когда звать: изучить API RUKS IDIAM, найти примеры, посмотреть Confluence-страницы
- Инструменты: Context7, GitHub Search, web search
- Режим: read-only

### Multimodal-looker
- **Анализатор медиа** — диаграммы, PDF, схемы, изображения из Confluence
- Когда звать: в документации есть диаграмма или скриншот, нужно извлечь смысл
- Режим: read-only

### Momus
- **Критик** — ревью планов, решений, документов на полноту и противоречия
- Когда звать: перед утверждением ADR, перед встречей, перед коммитом решения
- Задача: найти слабые места, blind spots, противоречия
- Режим: read-only

### Metis
- **Предпланирование** — анализ запросов перед началом работы
- Когда звать: новая задача или инициатива, нужно распаковать требования, найти скрытые intentions
- Режим: read-only

### BA Agent (Бизнес-аналитик)
- **Skill**: `po-ba`. Загрузить: `/po-ba` или `skill(name="po-ba")`. Вызов: `@BA: <задача>`
- **Анализ требований** — распаковка бизнес-требований в функциональные, написание acceptance criteria (два уровня: Given-When-Then для P0, лайт для P1+)
- **User Story Mapping** — помощь в структурировании пользовательских историй, гэп-анализ, приоритизация
- **Декомпозиция** — эпики → фичи → User Stories → задачи
- **Протоколирование** — ведение заметок встреч, извлечение решений и поручений
- **Глоссарий** — ведение единой терминологии проекта
- Когда звать: подготовка к встрече, анализ новых требований, уточнение acceptance criteria, декомпозиция эпиков
- Режим: read-only (анализирует документы) + write (оформляет протоколы, критерии)

### Sisyphus-Junior (через task с категорией)
- **Исполнитель** — пишет код, создаёт файлы, правит документы
- Категории:
  - `quick` — мелкие правки
  - `deep` — автономная проработка сложных тем (один goal за раз)
  - `ultrabrain` — очень сложные логические задачи
  - `visual-engineering` — всё что связано с UI/UX/фронтом
  - `writing` — документация, тексты, заметки
  - `unspecified-high/low` — остальное

### Компонентный файл (ACP 2.2.0.md)

```markdown
## [AIC-XXXX](https://jira.astralinux.ru/browse/AIC-XXXX) ❗ - Название задачи

**Статус:** <статус>
**Ответственный:** [[Работа/Astra/Команда/Команда Платформы AC/Имя|Имя]]
**Автор:** [[Работа/Astra/Команда/Команда Платформы AC/Имя|Имя]]

### Подзадачи
### ⛔ Блокеры

### Последнее изменение:
ДД.ММ.ГГГГ. Описание (Jira-переход или комментарий коллеги).

### Комментарии
На **ДД.ММ.ГГГГ - Статус команды:** ...
```

**Правила:**
- **Автор:** обязателен для всех родительских задач. Для членов команды - Obsidian-ссылка, для внешних - просто имя
- **Последнее изменение:** заголовок `###` (не `**`), дата с новой строки. Отражает Jira-переходы и развёрнутые комментарии коллег
- **Комментарии:** `### Комментарии` (множественное), формат: `На **ДД.ММ.ГГГГ - Статус команды:** ...`
- Jira-ссылки: в заголовке задачи и в перекрёстных упоминаниях (`[AIC-2079](url)`)
- 🔵 = Backlog, 🟢 = "в работе"/"In Progress", ❗ = последнее изменение >14 дней назад
- `### Комментарий` (ед.ч.) -> `### Комментарии` (мн.ч.)

### Заметки встреч (быстрый формат)
- Frontmatter: tags, created, updated
- Заголовок: `# Встреча ДД-ММ-ГГГГ - Тема`
- Разделы: Участники, Повестка, Ключевые решения, Задачи, Открытые вопросы, Связанные заметки
- Emoji-индикаторы: 🔴 🟠 🟡 ✅ ❓
- Формат имени: `ДД-ММ-ГГГГ-тема.md`

### ADR (Решения.md)
- Дата, контекст, решение, последствия
- Ссылка на источник (встреча или документ)

### Риски
- Формат: таблица с колонками #, Уровень, Риск, Последствия, Что делаем, Статус
- Уровни: 🔴 🟠 🟡 🟢 ✅

### Заметки с вопросами
- Frontmatter + ссылка на источник
- Вопрос, Ответ (после получения)

### Общее
- Связанные заметки через `[[линки]]`
- Трансклюзия содержимого: `![[Заметка#Раздел]]`
- Теги в frontmatter для поиска и группировки
- Устаревший контент помечать зачёркиванием `~~` или меткой `✅`, не удалять

## 5.5. Референсные облачные провайдеры

При проектировании архитектуры SCP и ACP ориентируемся на подходы следующих провайдеров:

### Эталон (международный опыт)
| Провайдер | Чему учимся |
|-----------|-------------|
| **Google Cloud (GCP)** | Операционно-ориентированный подход (202 + Operation) — стандарт индустрии. API design, resource-oriented design |
| **Microsoft Azure** | Enterprise-архитектура, N-1 версионирование, ARM template / Bicep для IaC |
| **IBM Cloud** | Enterprise multi-tenancy, IAM модели |

### Российский рынок  
| Провайдер | Чему учимся |
|-----------|-------------|
| **Yandex Cloud** | Единственный на РФ, кто следует GCP-стандарту (202+Operation). API-дизайн, документация, UX портала |
| **Cloud.ru** | Partner API (подробно разобрано в [[Partner API]]). Модель тенантов, IAM, квоты. Ближайший аналог по архитектуре |
| **Selectel** | Ресурсно-ориентированный подход. Простота и прагматичность |
| **VK Cloud** | Ресурсно-ориентированный подход. Российская специфика |

### Не референс (но знать)
| Провайдер | Почему |
|-----------|--------|
| **DigitalOcean** | Слишком простой API, не подходит для enterprise multi-tenancy |
| **OpenStack** | Устаревшая модель API (не RESTful, XML-RPC), но используется внутри ACP (Crystal BE) |

## 6. Правила работы

### Confluence
- Credentials в `.env` (НЕ КОММИТИТЬ)
- Скрипт: `bash scripts/sync-confluence.sh <command> <args>`
- Команды: `get`, `update`, `search`, `list`
- Зависимости: `curl`, `jq`
- Экспортированные страницы сохраняются в `confluence/` с frontmatter (title, page_id, version, space, source)

### Jira (только READ-ONLY)
- Credentials в `.env` (`JIRA_TOKEN`)
- Скрипт: `bash scripts/jira-read.sh <command> <args>`
- Команды:
  - `board <id>` — информация о доске
  - `issues <board-id> [N]` — список задач на доске
  - `issue <key>` — детали конкретной задачи
  - `search <cql>` — поиск по CQL-запросу
  - `myself` — текущий пользователь
  - `columns <board-id>` — колонки доски
- **НИКАКИХ ИЗМЕНЕНИЙ** через API — только чтение
- Доска ACP Board: ID 1783
- Основной проект: AIC

### Obsidian
- Все файлы в корне SCP/ — markdown
- Внутренние ссылки: `[[Заметка]]`
- Трансклюзия: `![[Заметка#Раздел]]`

## 8. Принципы работы

1. **Read-only прежде всего** — прежде чем писать, прочитай существующие документы
2. **Не переписывай историю** — ADR и встречи не меняются post-factum, только дополняются
3. **Одна заметка — одна тема** — не мешай встречи, ADR и риски в одном файле
4. **Все решения — в ADR** — устные договорённости не считаются, пока не записаны
5. **Связанные заметки** — всегда ставь `[[линки]]` между связанными документами
6. **Не удаляй** — если контент устарел, помети `~~зачёркнутым~~` или `✅`, но не удаляй
7. **Фамилии → модули** — в документах для внешнего показа (Confluence, К просмотру/) и в разборе US заменяй фамилии участников на названия модулей:
   - Шадрин → IaaS-оркестратор
   - Югай → IAM
   - Склабовский → BillManager
   - Перевалов → SCP / Product Owner
   - Тайлаков → IAM / SDN
   - Иволга → SDN
   - Мордвин → BA
   - Пронюшкин → Архитектор платформы
   - Руслан (Курбанов) → Дизайнер
   - Внутренние заметки (Встречи/, 1-to-1/) — фамилии сохраняются для контекста
8. **Комментарии в Confluence → заметки в Obsidian** — при появлении новых комментариев на Confluence-страницах проекта создавай заметку в `ревью/` с разбором вопроса, контекстом и предлагаемым решением. Ссылайся на релевантные US и ADR.

## 9. Механизм восстановления после сбоев

> **Когда что-то пошло не так — не паниковать, действовать по схеме.**

### 9.1. Типы сбоев и их признаки

| Тип | Признаки | Типичная причина |
|-----|----------|-----------------|
| **🔌 Плагин отвалился** | Инструмент не отвечает, таймаут, `non 2xx status code` при работающем API | Перегрузка, конфликт версий, MCP сбой |
| **🐌 Зависший скрипт** | Команда не завершается за ожидаемое время (30с+) | Бесконечный цикл, регекс, большой объём данных |
| **💥 Дублированное форматирование** | Один и тот же блок встречается 2-3 раза в файле | Повторный прогон скрипта поверх уже обработанных данных |
| **🔐 Confluence 401/403** | `HTTP 401` или `HTTP 403` при запросе к API | PAT-токен протух, нет прав на страницу |
| **📄 Confluence 404** | `HTTP 404` при запросе страницы | Страница удалена или ID неверный |
| **🔄 CalDAV не отвечает** | Пустой ответ или таймаут при запросе календаря | Неверный URL, нет библиотеки, сервер недоступен |

### 9.2. Схема восстановления (пошагово)

```
Шаг 1️⃣  ДИАГНОСТИКА (5 секунд)
  └─ Что именно упало? (инструмент, скрипт, API, файл)
  └─ Сообщить пользователю: "Сбой [тип]: [причина]"
  
Шаг 2️⃣  ИЗОЛЯЦИЯ
  └─ Если завис скрипт → pkill -f "script-name"
  └─ Если плагин → отметить DEGRADED, не использовать
  └─ Если данные испорчены → остановить запись

Шаг 3️⃣  Graceful Degradation (чем заменить)
  └─ Браузер упал → curl/webfetch для HTTP
  └─ LSP упал → работаем без автодополнения
  └─ Confluence API упал → работаем с локальными копиями
  └─ Python скрипт завис → bash + sed/awk как fallback

Шаг 4️⃣  ВОССТАНОВЛЕНИЕ ДАННЫХ
  └─ Если файл испорчен (дубли, битый frontmatter):
      1. Перекачать из Confluence (если есть page_id)
      2. Если нет — восстановить frontmatter из `.sync-state.json`
      3. Если и там нет — создать заново из Confluence API
  └─ Если локальная копия устарела: `python3 sync-confluence.py`

Шаг 5️⃣  PREVENTION (на будущее)
  └─ Записать в лог: дата, сбой, что сделали
  └─ Если повторяется 2+ раза → создать правило в AGENTS.md
```

### 9.3. Конкретные fallback-ы для каждого инструмента

| Инструмент | При сбое используем |
|-----------|---------------------|
| `playwright_browser_*` | `webfetch` для чтения, `curl` для API |
| `lsp_diagnostics` | Пропускаем, работаем вслепую |
| `confluence_api` | `confluence/*.md` локальные копии |
| `sqlite` / `caldav` | `curl` прямой запрос к SOGo |
| `task()` (субагент) | Пробуем ещё раз, если 2+ неудач → делаем сам |
| `sync-confluence.sh` | `sync-confluence.py` как альтернатива |

### 9.4. Anti-patterns (что НЕ делать при сбое)

- ❌ Не запускать тот же скрипт повторно на уже испорченных данных — сначала откатить
- ❌ Не множить fallback-попытки (максимум 2 ретрая)
- ❌ Не игнорировать сбой и продолжать — данные разъедутся
- ❌ Не удалять файлы «чтобы пересоздать» — сначала убедиться, что есть чем восстановить
- ❌ Не писать поверх испорченного файла новым скриптом — сначала откатить до оригинала

### 9.5. Быстрые команды для ручного восстановления

```bash
# Перекачать одну страницу из Confluence
bash scripts/sync-confluence.sh get <page-id> <output.md>

# Проверить все страницы на обновления
export CONFLUENCE_PAT="$(grep CONFLUENCE_TOKEN .env | cut -d= -f2)"
python3 confluence/sync-confluence.py --check

# Найти файл по page_id в frontmatter
grep -rl "page_id: 478214117" SCP/confluence/

# Последние ошибки синхронизации
tail -20 SCP/confluence/sync-log.md
```
