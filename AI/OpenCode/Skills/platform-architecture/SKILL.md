# platform-architecture - видение и целевая архитектура ACP

Канонический контекст архитектуры платформы. Используется при анализе встреч для выявления расхождений между обсуждаемым и утверждённой концепцией.

---

## Архитектурные принципы

1. **Разделение target и baseline.** Целевая референс-архитектура и baseline конкретного релиза - разные артефакты. Не смешивать в одном обсуждении.
2. **4-plane модель:** Service Control Plane (оркестрация, порталы) -> Commerce Plane (биллинг) -> Reliability Plane (мониторинг, бэкап) -> Ecosystem Plane (XaaS, Boatsman)
3. **API-стандарт:** RESTful JSON, OAuth2/OIDC, Platform Context (Security + Tenant), BFF-паттерн между порталами и компонентами
4. **BillManager - только биллинг** в целевой картине. Не портал, не оркестратор, не провижининг.
5. **Тенант - простая сущность.** Контейнер ресурсов. Поведение (состояния, привязка к организациям) - через оркестратор.
6. **Внешние зависимости - минимизировать.** FreeIPA вместо ALD Pro. RuBackup - опционально, только для пользовательских нагрузок.

---

## Границы компонентов

| Компонент | Зона ответственности | С чем работает |
| --- | --- | --- |
| **IaaS Orchestrator** | Провижининг IaaS-ресурсов | Брест (ВМ, диски), SDN/APOS (сети) |
| **PaaS Orchestrator** | Провижининг PaaS-ресурсов | Boatsman (managed Kubernetes) |
| **TMS** | Контейнеры изоляции | Группы (Брест), namespaces (Боцман), VDC |
| **Organization Manager** | Иерархия организаций (отдельно от ТМС) | Над ТМС |
| **Quota Manager** | Квоты по ресурсам | Платформенная capability, не часть биллинга |
| **API Gateway** | Единый слой между порталами и компонентами | Два контура: внутренний + внешний |
| **BillManager** | Только биллинг в целевой картине | Синхронизация ресурсов, тарификация |

---

## Ключевые решения (ратифицированные)

- **FreeIPA** - во всех новых редакциях (заменяет ALD Pro). ALD только в Base.
- **RuBackup** - опционально, только пользовательские нагрузки. Бэкап платформы - через Brest + ACCM.
- **Редакции ACP:** Light, Certified, Base, Pro + Addon (Boatsman).
- **IAM в Brest** - через Libvirt, с пересертификацией. Цель: май 2027.
- **Обработчики услуг BillManager** - пишем сами (как Boatsman), не просим команду BillManager.

---

## Решения на стадии обсуждения

- **Целевая архитектура:** 3-слойная схема Пронюшкина не ратифицирована. Андрей Крюков считает её «оторванной от реалий».
- **Organization Manager:** отдельный компонент или внутри ТМС - не решено.
- **Usage metering:** как платформенная capability (не биллинг) - не зафиксировано.
- **Полный отказ от BillManager:** не решён, зависит от альтернативы.

## Глоссарий

| Термин | Значение | Где используется |
| --- | --- | --- |
| VDC | Контейнер изоляции в Бресте | Только на последней стрелке в Брест |
| Тенант / Проект | Синонимы в UI. Тенант - техническая сущность, проект - пользовательская | Портал самообслуживания |
| Организация | Группировка тенантов | Organization Manager |
| Обработчик услуги | Механизм интеграции BillManager с ресурс-провайдером | BillManager |
| TMS | Tenant Management System | Управление контейнерами изоляции |
| BFF | Backend-for-Frontend | API-слой между порталами и компонентами |
