# meeting-protocol - протокол + анализ встречи

Составляет и анализирует встречу: от транскрибации до готовой заметки.

**Источник стенограмм:** папка `Работа/Astra/Встречи/Стенограмма встреч/` в vault.
Если файл `.doc` - прочитать, конвертировать в `.md`, удалить `.doc`. Если файла нет - спросить пользователя.

На выходе - **единая Obsidian-заметка** со всеми разделами inline.

**Эталон:** `Работа/Astra/Встречи/Протоколы встреч/Архитектура/2026-07-07 Архитектура ACP 2.2-2.3`
Всегда читай эталон перед написанием протокола и воспроизводи его структуру и стиль точно.

## Связанные заметки

После протокола - указать связанные встречи, на которые повлияли результаты текущей. Для каждой: что именно изменилось/прояснилось.

```markdown
- **[[YYYY-MM-DD <Название>]]** - <что меняется>:
  - <пункт 1>
  - <пункт 2>
```

**После создания протокола - ОБЯЗАТЕЛЬНО:**
1. Открыть каждую связанную заметку
2. Добавить в неё ссылку на текущий протокол в соответствующие разделы (решения, риски, зависимости, AAR)
3. Обновить контент связанной заметки с учётом новой информации (изменить статусы, сроки, решения)
4. Если связанная заметка сама имеет `## Связанные заметки` - дополнить их
5. **Обновить сводную prep-заметку серии.** Конкретные действия:

   a. Обновить `**Прошедшая встреча:**` - ссылка на текущий протокол
   b. Обновить `**Следующая встреча:**` - если известна дата следующей
   c. Добавить протокол в `# Предыдущие встречи`
   d. Обновить `# Контекст предыдущей встречи` - перенести решения (со статусами ✅/⏳/🔴), общие задачи
   e. Обновить раздел `# Встречи` - статусы проведённых/непроведённых

   Если сводной заметки нет - создать по шаблону из `meeting-prep`.

| Серия | Prep-заметка |
| --- | --- |
| Архитектура ACP | `Протоколы встреч/Архитектура/Архитектура ACP.md` |
| Синки команды | `Протоколы встреч/Синки команды/Синки команды.md` |
| Синки с BillManager | `Протоколы встреч/Синк с BillManager/Синки с BillManager.md` |
| Синки с ИБ | `Протоколы встреч/Синки с ИБ/Синки с ИБ.md` |
| Синки с RnD | `Протоколы встреч/Синки с RnD/Синки с RnD.md` |
| UseCase ЛК | `Протоколы встреч/Командные нерегулярные встречи/Разбор UseCase для ЛК.md` |

### Структурный анализ (для архитектурных встреч)

Для архитектурных встреч - **обязательно** добавлять раздел `## Анализ стенограммы` после AAR:

- **Главный тезис** - в чём корневая проблема встречи, что на самом деле произошло (а не о чём говорили)
- **P0 - блокеры** - структурные конфликты, неразрешённые дилеммы, нарушение слоёв
- **P1 - исправить до финализации** - мис-скоупленные компоненты, неверные границы
- **P2 - гигиена** - терминология, naming, оформление схем
- **Расхождение с текущей концепцией** - выявленные противоречия между обсуждаемым и утверждённым видением платформы. Сверять с каноническим контекстом из скилла `platform-architecture`. По каждому расхождению: что в концепции vs что на встрече + предлагаемое разрешение
- **Вопросы** - к архитектору или на эскалацию
- **Последующие шаги** - конкретные действия к следующей встрече (кто/что/когда)

Для остальных встреч (синки команды, 1-2-1, etc.) - если виден структурный конфликт или архитектурная дилемма, предложить пользователю добавить такой разбор.

## Pipeline (от транскрибации к заметке)

### Шаг 0: Сбор контекста (ОБЯЗАТЕЛЬНО перед написанием)

**ПРОВЕРКА ТИРЕ:** Перед записью любого текста убедись, что используется только дефис `-` (U+002D), а не длинное тире `-` (U+2014). В macOS длинное тире вводится через Option+Shift+дефис - НЕ ИСПОЛЬЗОВАТЬ.

**0.5 Стенограмма: конвертировать и привязать (ОБЯЗАТЕЛЬНО)**

Если стенограмма предоставлена файлом (`.doc`, `.txt`):
1. Конвертировать `.doc` в `.md`: `textutil -convert txt "файл.doc" -output "/tmp/название.txt"`
2. Скопировать в vault: `cp "/tmp/название.txt" ".../Стенограмма встреч/Название_YYYY-MM-DD.md"`
3. Удалить исходный `.doc`/`.txt`
4. Добавить в протокол: `Стенограмма: "[[Стенограмма встреч/файл.md|Название]]"` в frontmatter и в `## Связанные заметки`

Если файла нет - спросить пользователя.

Перед тем как писать протокол - собери контекст из трёх источников:

**1. Предыдущий протокол той же серии встреч**
- Найди в `Работа/Astra/Встречи/Протоколы встреч/<та же папка>/` заметку с ближайшей предыдущей датой
- Прочитай разделы `## Задачи` и `## Решения`
- Выпиши задачи, у которых срок <= дата текущей встречи - они должны были быть выполнены
- Сравни с тем, что упоминается в транскрибации: если задача не упомянута - она либо тихо закрыта, либо упущена
- Упущенные/невыполненные задачи добавь в `### Контекст` протокола с пометкой «перенесено с предыдущей встречи» и продли в `## Задачи`
- **ОБЯЗАТЕЛЬНО: после написания протокола - вернуться в предыдущий протокол и отметить задачи как `[x]`**:
  - Задачи, выполненные к встрече - `✅ 2026-07-27` (дата закрытия)
  - Задачи, перенесённые в новый протокол - `✅ перенесено в 2026-07-27` (чтобы `tasks` не показывал дубли)
  - Задачи в заметках коллег (в `Команда Платформы AC/<Имя Фамилия>.md`) - **убирать ручные `[ ] #teamsync` чекбоксы** если они дублируют протоколы. `tasks` блок в заметке коллеги сам соберёт актуальные задачи

**2. Prep-заметка (подготовка к этой встрече)**
- Найди в `Работа/Astra/Встречи/Подготовка ко встречам/YYYY-MM-DD <Название>.md`
- Прочитай вопросы, риски и открытые темы - они должны были быть обсуждены
- Если тема из prep не прозвучала на встрече - отметь в `## AAR` как «не обсудили»

**3. Протоколы смежных встреч (если есть)**
- Если в транскрибации упоминаются встречи с внешними командами (Bill, RooX, Boatsman и т.д.) - найди их протоколы
- Используй как дополнительный контекст для зависимостей и решений

**4. Открытые вопросы (для всех типов встреч - обязательно)**

Перед написанием протокола проверь, какие открытые вопросы закрылись на встрече, а какие остались.

**Источники открытых вопросов:**
- **Предыдущий протокол той же серии** - разделы `## Задачи` и `## Открытые вопросы`
- **Prep-заметка** - раздел с вопросами/открытыми темами
- **Заметка коллеги** (для 1-2-1) - `Команда Платформы AC/<Имя Фамилия>.md`, раздел `# Открытые вопросы`

**Алгоритм проверки:**
1. Собери список всех открытых вопросов из источников выше
2. По транскрибации определи, какие из них обсуждались на встрече
3. **Закрытые** - убери из источника (заметка коллеги / prep), ответ зафиксируй в протоколе в разделе `## Решения`, а факт/знание - в `# Знания` или странице компонента
4. **Не закрытые, но обсуждавшиеся** - обнови формулировку по итогам обсуждения
5. **Новые открытые вопросы**, прозвучавшие на встрече - добавь в источник

**В протоколе встречи:** добавь раздел `## Открытые вопросы` с таблицей:

| Вопрос | Источник | Статус |
| --- | --- | :---: |
| <вопрос> | [[предыдущий протокол]] / [[prep-заметка]] / новое | ✅ закрыт / ⏳ в работе / 🔴 открыт |

Закрытые вопросы дублируются в `## Решения` с формулировкой ответа.

### Шаг 1: Протокол встречи
- Прочитать транскрибацию/стенограмму

- Опираться на финальные формулировки ведущего

### Шаг 2: Решения
- Только реальные решения, принятые на встрече - без поручений
- Решение = договорённость, принцип, выбор направления
- Каждое решение - одна строка: `**<Тема>** - <что решили>`

### Шаг 3: Задачи
- Таблица (кому / что / срок) + чекбоксы для Obsidian Tasks
- Чекбоксы: `#тег-встречи #Фамилия_Имя` + `📅 YYYY-MM-DD` если есть срок

### Шаг 3.1: Риски
- Выписать риски, прозвучавшие на встрече, с цветовой кодировкой 🔴🟠🟡
- Формат: `**<Риск>** - 🔴 <описание и последствия>`

### Шаг 3.2: Требуются отдельные обсуждения
- Темы, которые не смогли закрыть на встрече и требуют отдельной встречи
- Таблица: Тема | Участники | Причина | Следующий шаг

### Шаг 3.3: Открытые вопросы
- Сверить с источниками из Шага 0.4: что закрылось, что осталось, что добавилось
- Таблица: Вопрос | Источник | Статус (✅ закрыт / ⏳ в работе / 🔴 открыт)
- Закрытые вопросы продублировать в `## Решения` с ответом
- Обновить источники (заметка коллеги, prep-заметка, предыдущий протокол)
- **Чекбоксы остаются в протоколах.** Prep-заметка использует `tasks` блоки для динамического сбора открытых задач (см. `meeting-prep`)

### Шаг 4: Анализ
- 5 главных тем с компонентами ACP
- DACI-матрица для ключевых решений

### Шаг 5: Зависимости
- Цветовая кодировка: 🔴 блокер / 🟠 сильно / 🟡 слабо / ⚪ неопределено / ✅ готово

### Шаг 6: Портреты
- Поведенческие профили ключевых участников
- Роль, стиль, триггеры, цитата, вклад

### Шаг 7: Стейкхолдеры
- Таблица: Стейкхолдер | Интерес | Влияние | Квадрант + описание

### Шаг 8: AAR
- Удачно / Неудачно / Почему / Что делать иначе + метрики

## Правила оформления

- Тире в тексте: только дефис `-`, не длинное тире `-`
- Frontmatter `Время`: `"11:30-13:00"` (кавычки, дефис)
- Имена в тексте: `@Имя Фамилия`, в ссылках: `[[Имя Фамилия]]`
- Заголовок файла: `YYYY-MM-DD Название` (сортировка по убыванию - новые сверху)
- Сохранять в Obsidian сразу, без показа черновика

### Правила для Jira-статусов в prep-заметках

- **Статус с датой обновления:** `<статус>` (обновлено ДД.ММ) - обязательно даже для неизменных
- **Ответственный:** Имя Фамилия - указывать для каждой задачи
- **❗ маркер висяка:** если статус не обновлялся >14 дней - ставить `❗` после номера, перед названием
- **Комментарии:** Последний комментарий (ДД.ММ, ЧЧ:ММ): Имя - текст. Предыдущий (если был)
- **Подзадачи:** если есть - список с ссылками, статусами и датами обновления
- **Блокеры:** если есть - перечислить ключи (BREST-XXXX, AIC-XXXX)

### Правила переноса задач между протоколами

- При создании нового протокола - вернуться в предыдущий и отметить задачи:
  - Выполненные: `[x] ... ✅ YYYY-MM-DD`
  - Перенесённые в новый протокол: `[x] ... ✅ перенесено в YYYY-MM-DD`
- Заметки коллег (`Команда Платформы AC/<Имя>.md`): **не дублировать** `#teamsync` чекбоксы вручную. `tasks` блок сам соберёт из протоколов

`Работа/Astra/Встречи/Протоколы встреч/<папка-типа>/YYYY-MM-DD <Название>.md`

Папки по типам встреч:
- Синки команды - `Синки команды/`
- Архитектурные - `Архитектура/`

Протокол - в раздел `# Cинки`, подзаголовком `### YYYY-MM-DD - 1-2-1`. Формат компактный: протокол (короткими пунктами) -> решения -> задачи (с чекбоксами) -> AAR. **Связь с подготовкой:** если есть prep-заметка `YYYY-MM-DD <Название>.md` в `Подготовка ко встречам/` - добавить взаимные ссылки.
