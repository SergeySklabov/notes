# meeting-digest - анализ протоколов встреч

Извлекает из стенограммы/протокола встречи полный набор артефактов: роли (DACI), карту зависимостей, портреты участников, карту стейкхолдеров, AAR.

## Использование

Загрузи скилл:

```
skill(name="meeting-digest")
```

Вызов:

```
@Atlas: /meeting-digest file=<путь-к-файлу> out_dir=<путь-для-артефактов>
```

Пример:

```
@Atlas: /meeting-digest file=Работа/Astra/Встречи/15-06-2026-протокол.md out_dir=Работа/Astra/Встречи/Артефакты
```

## Параметры

| Параметр | Обязательный | Описание |
|----------|:------------:|----------|
| `file` | ✅ | Путь к файлу протокола/стенограммы встречи (абсолютный или относительно Obsidian vault) |
| `out_dir` | ❌ | Директория для сохранения артефактов. По умолчанию - рядом с файлом, в подпапке `Артефакты/<дата>/` |

## Что делает

### Контекст проекта

Скилл работает в контексте облачной платформы **Astra Cloud Platform (ACP)**. Ключевая особенность: вопросы и решения на встречах могут затрагивать **несколько компонентов платформы** и **несколько ответственных** одновременно.

**Компоненты ACP:** IAM (UIDM), Брест (VIT), SDN (APOS), SCP (Личный кабинет), TMS, BCKP (Резервное копирование), CTR/K8s, MON (Мониторинг), BIL (Биллинг), SDS (TROK), APIM, REP.

При анализе учитывай cross-component связи и пересечение зон ответственности.

### Шаг 1: Сырой анализ

- Прочитать стенограмму/протокол
- Выписать: участники, повестка, ключевые цитаты
- Определить 3-5 главных тем с указанием затрагиваемых компонентов
- Сохранить: `{out_dir}/Анализ встречи <дата> - <тема>.md`

### Шаг 2: Решения и поручения

- Таблица решений: что решено, кто решил, какие компоненты затронуты, последствия
- Таблица поручений: кому, что, срок, какие компоненты
- Сохранить: встроено в анализ

### Шаг 3: DACI-матрица

- Для каждого ключевого решения:
  - **Driver** - кто ведёт тему, готовит решение
  - **Approver** - кто утверждает
  - **Contributors** - кто даёт экспертизу
  - **Informed** - кого ставят в известность
- Учитывать cross-component DACI: одно решение может иметь нескольких Driver'ов из разных компонентов
- Сохранить: `{out_dir}/DACI - <дата> <тема>.md`

### Шаг 4: Матрица зависимостей

- Что от кого/чего зависит (внутрикомандные и межкомпонентные)
- Цветовая кодировка: 🔴 блокер 🟠 сильно 🟡 слабо ⚪ неопределено ✅ готово
- Явно отмечать зависимости между разными компонентами ACP
- Сохранить: `{out_dir}/Зависимости - <дата> <тема>.md`

### Шаг 5: Портреты участников

- Поведенческие профили ключевых участников с цитатами и триггерами
- Отмечать амплуа (архитектор, ТПМ, разработчик, аналитик) и чью сторону представляет
- Сохранить: `{out_dir}/Портреты - <дата> <тема>.md`

### Шаг 6: Карта стейкхолдеров

- Power/Interest Grid с участниками встречи
- Явно указывать, какой компонент представляет каждый стейкхолдер
- Сохранить: `{out_dir}/Стейкхолдеры - <дата> <тема>.md`

### Шаг 7: AAR (After-Action Review)

- 4 вопроса: что планировали -> что получилось -> почему -> что будем делать иначе
- Добавить метрики: количество решений, поручений, открытых вопросов
- Сохранить: `{out_dir}/AAR - <дата> <тема>.md`

## Модели

### DACI

- **Driver** - кто ведёт тему, готовит решение
- **Approver** - кто утверждает
- **Contributors** - кто даёт экспертизу
- **Informed** - кого ставят в известность

### Power/Interest Grid

- **Key Players** (HP/HI) - активно вовлекать
- **Keep Satisfied** (HP/LI) - управлять
- **Keep Informed** (LP/HI) - держать в курсе
- **Monitor** (LP/LI) - отслеживать

### AAR

- 4 вопроса: планировали -> получилось -> почему -> иначе
