**Проект.** Волонтёрский community-бот в Telegram: структурирование чатов, антиспам, чёрные списки. ~1500 групп. С первого дня — требование tenant isolation, никакие данные не должны утечь.

**Команда.** 2 активных разработчика (бывало 4–5). Илья по основной работе — архитектор embedded-систем в автоиндустрии (управление двигателями, термальные системы, батареи). Веб делал лет 8 назад. Бот — волонтёрский. Бюджет ≈ 0, поэтому каждое решение оптимизировалось под "минимум усилий → быстрая проверка".

**Почему изначально Vercel**

·       Не нужно поднимать VPS / Docker / k8s

·       Веб-редактор (по типу CodePen) — править из браузера без IDE и Git

·       One-click deploy в staging и prod

·       GitHub-раннеры от Vercel сами разворачивают код

·       Google Sheets как админка — не пришлось писать фронт

**Триггер миграции (комбинация)**

1.     Vercel молча терял Telegram-сообщения (HTTP 200 при падении)

2.     Telegram не поддерживает очереди — потерянное сообщение потеряно навсегда

3.     Enterprise-тариф закрывал только надёжность, без других бенефитов — экономически бессмыслен

4.     Цена росла; $60/мес → впереди только хуже

**Почему миграция оказалась лёгкой**

·       У Ильи на основной работе уже есть production-опыт с Kubernetes

·       Бот был в основном session-less — переключение узлов прошло без сложного state transfer

·       Для бесшовного переезда сделали самописную очередь через Postgres: обе площадки писали/читали туда, чаты переносили по одному ~2 недели

**Главное (с явной оговоркой N=1).** Твоя гипотеза о гэпе между Heroku/Vercel и облаком частично подтверждается, но кейс Ильи показывает критичный нюанс: **в его сегменте гэпа нет**, и он сам тебе об этом сказал, не назвав это прямо.

Илья мигрировал быстро и дёшево потому, что:

1.     У него уже был коммерческий опыт с k8s с основной работы — "бесплатный"

2.     Бот изначально был session-less — архитектурный подарок

3.     Команда инженерно зрелая

4.     Инфра маленькая ($6–7/мес) — любая подписка > этой цифры неконкурентна

**То есть Илья — анти-ICP для DeployCode**. Он бы DeployCode не купил. Это плохая новость, если ты хотел его конвертировать, но **хорошая** — он чистый кейс "что вижу со стороны рынка".

**Где тогда ICP DeployCode** (гипотеза для следующих интервью):

·       Команды без production-K8s опыта внутри

·       Команды, где приложение **stateful** — то, что у Ильи было session-less, у большинства не так, и миграция в разы больнее

·       Команды, для которых $60/мес терпимо, но $300/мес — катастрофа (т.е. они на стадии масштабирования)

·       Команды, которые **боятся** миграции и поэтому пересиживают на Vercel/Heroku дольше экономически разумного

**Что ценного вытащили для product'а**

То, за что Илья любил Vercel — DeployCode должен это сохранить:

·       Zero setup (никакого VPS/Docker/k8s)

·       Web editor (без локалки)

·       One-click deploy (staging + prod)

·       GitHub auto-runner

То, чего Илье критически не хватало на Vercel — DeployCode должен закрывать сильно лучше:

·       **Прозрачность отказов** — Vercel возвращал 200 OK при потере сообщения, это худший сорт отказа

·       **Graceful degradation** — на Vercel её "вообще никакой"

·       **Контролируемый рестарт пода** — чтобы Telegram понял, что сообщение надо переслать

·       **Нормальные логи**

Это твоё позиционирование для технической аудитории, в одну фразу: **"Vercel-like ergonomics, K8s-like reliability."**

**Цифры, которые стоит проверять на каждом следующем интервью**: цена на Vercel/Heroku перед уходом, цена своей инфры после, время миграции, бэкграунд в K8s в команде, размер команды на миграцию.
