Адженда

  1. Введение: что такое IaaS-orchestrator, его место в архитектуре ACP
  2. Платформенный контекст: безопасность, изоляция, технические условия
  3. Контекст безопасности - протоколы, токены, валидация
  4. Контекст изоляции - VDC, тенанты, границы выполнения запросов
  5. План следующих встреч

5 главных тем

  1. IaaS-orchestrator = центральный управляющий компонент для автоматизации ЖЦ IaaS-ресурсов (VM, volume, image). Цель - майский релиз 2027
  2. Платформенный контекст - структурированный набор метаданных, сопровождающий каждый запрос: кто, имеет ли право, в каких границах, в каких технических условиях
  3. JWT-токены + OIDC - выбранный протокол безопасности (Authorization Code Flow + Client Credentials Flow). JWT на первых релизах, opaque-токены в будущем
  4. VDC = тенант - контейнер изоляции. IaaS-orchestrator хранит конфигурацию VDC (кластер, узлы, хранилища, сеть) для привязки ресурсов к конкретному тенанту
  5. Зависимости от смежных систем - ТМС (тенанты), ИАМ (аутентификация/авторизация), Billing (проверка доступности), Quota Manager, Resource Usage

2026-06-17 Архитектурный комитет. IaaS-orchestrator. Оркестрация запроса

Протокол встречи

Событие: Архитектурный комитет. IaaS-orchestrator. Механика оркестрации запроса Стенограмма: “Арх.ком.ACP_IaaS-orc_2026-06-10” Дата: 17.06.2026, 12:00-13:00 Участники: @Александр Шадрин, @Сергей Склабовский, @Дмитрий Попенов, @Дмитрий Пронюшкин, @Алексей Боровиков, @Виталий Козловский Запись: https://dion.vc/video/

Адженда

  1. Проблема: синхронные запросы при длительных операциях -> зомби-ресурсы, таймауты
  2. Вариант A: синхронная цепочка вызовов - отклонён
  3. Вариант B: event-driven архитектура (Kafka, Rabbit) - отклонён
  4. Вариант C: синхронный запрос -> задача в БД -> фоновая обработка - принят
  5. Практический пример: создание тенанта
  6. Дискуссия: таски vs сущности, распределённые транзакции, идемпотентность

5 главных тем

  1. **Архитектура оркестрации: синхронная фаза (валидация, блокировка) + асинхронная фаза (worker + state machine) с хранением шагов в БД (PostgreSQL, SELECT FOR UPDATE SKIP LOCKED)
  2. State machine: PENDING -> RUNNING -> COMPLETED/FAILED/CANCELLED. Шаги сохраняются атомарно - возобновление после падения с последнего успешного шага
  3. Идемпотентность - единственное требование к смежным системам (повторный запрос не создаёт дубликат)
  4. Риск бутылочного горлышка - если IaaS-orchestrator станет центральным оркестратором для всех сущностей платформы
  5. «N+1 оркестраторов» - платформенный оркестратор (OSS/BSS) логически отделен от IaaS-orchestrator, но в релизе 2.2 функционально размещается внутри IaaS-orchestrator с отчуждаемыми модулями
  6. Нет распределённых транзакций - только локальные транзакции в БД orchestrator. Сбой в смежной системе -> retry -> FAILED -> клиент возобновляет вручную

Как устроена оркестрация

Запрос -> REST Controller -> бизнес-логика -> задача в БД (PENDING)
                                                  |
                                          Планировщик (worker)
                                                  |
                                          SELECT ... FOR UPDATE SKIP LOCKED
                                                  |
                                          Диспетчер -> Обработчик
                                                  |
                                          State Machine (шаги)
                                                  |
                                          COMPLETED / FAILED / CANCELLED

Рекомендации

До встречи

  1. Материалы за 48ч - Александр выкладывает ADR/слайды за 2 рабочих дня до встречи. Если не готово - встреча переносится
  2. Пре-ридинг - участники читают и оставляют комментарии в документе (не в чате). Комментарии - обязательное условие участия
  3. Форма «Вопросы к встрече» - каждый участник пишет 1-3 вопроса в Google Doc за 24ч до встречи. Вопросы группируются по темам
  4. Чёткий адженда - темы + timebox + expected outcome (решение / информация / brainstorming)

На встрече

  1. Timebox на тему - 15-20 мин максимум. В конце - решение за 2 мин
  2. Одна тема = одно решение - не обсуждать 2 несвязанные темы за одну встречу
  3. Модератор - выделить человека (не автора), который следит за таймингом и не даёт уходить в детали
  4. Формат ADR - Architecture Decision Record перед каждой встречей: контекст -> варианты -> решение -> последствия
  5. Запрет на смешение релизов - обсуждать либо тактику (2.2), либо стратегию (целевая архитектура). Если тема переходит границу - завести отдельную встречу
  6. Видео-запись - включена и разослана всем участникам (уже есть, зафиксировать как стандарт)

После встречи

  1. Протокол за 24ч - протокол решений и задач рассылается на следующий день
  2. Pull Request на ADR - каждое решение оформляется как PR в репозиторий архитектуры. Участники аппрувят в течение недели
  3. Ретроспектива формата - раз в месяц 10 мин: что работает, что нет, что изменить

AAR

1. Что планировали?

Обсудить платформенный контекст (безопасность, изоляция) и принять архитектурные решения по IaaS-orchestrator.

2. Что получилось?

  • Приняты ключевые решения по контексту безопасности (JWT, OIDC)
  • Не успели обсудить механику тенантов (перенесено на 17.06)
  • Обсуждение биллинга и Resource Usage заняло значительное время без финального решения
  • На второй встрече принята архитектура оркестрации (state machine, async worker)

3. Почему?

  • Материалы не были разосланы заранее - часть времени ушла на введение
  • Биллинг/Quota/Resource Usage - нет предварительного исследования
  • Много смежных тем (платформенный оркестратор, эвент-драйвен) - обсуждение уходило в стратегию

4. Что будем делать иначе?

  • Материалы за 48ч до встречи
  • Чёткий адженда с timebox
  • Пре-ридинг и письменные вопросы до встречи
  • Одна тема - одно решение
  • Отдельные встречи для тактики (2.2) и стратегии (целевая архитектура)
