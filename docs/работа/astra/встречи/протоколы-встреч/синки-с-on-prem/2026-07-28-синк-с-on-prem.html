Протокол встречи

Тема: Первый регулярный синк ACP ↔ On-prem - ожидания, зоны ответственности, миграция, лицензии, бэкап Участники: @Сергей Склабовский, @Александр Кудрявцев, @Людмила Руденко, @Даниил Копцев, @Дмитрий Тайлаков

Контекст

Первая встреча из ежемесячной серии «Синк с On-prem» (команда внедрения/сопровождения). Цель - синхронизировать ожидания между командой ACP и On-prem, выявить совместные активности, которые нужно проработать и трекать. Встреча инициирована Сергеем, по необходимости частота может быть увеличена.

1. Список исправленных уязвимостей (CVE) для сертифицированных компонентов

Нужно ли собирать единый список CVE по всем компонентам платформы?

  • Позиция Людмилы: заказчики (например, Гринатом) могут запросить такой список. Единый документ под одной шапкой удобнее.
  • Позиция Александра: для аттестации ACP CVE не нужны - это атрибут сертификации. Каждый сертифицированный компонент (Brest, ALSI, LD Pro) и так публикует формуляр с CVE при релизе в Личном кабинете. Brest, ALSI, LD Pro - списки есть. Остальные компоненты не сертифицированы - списка нет.
  • Позиция Даниила: на данном этапе отдельные списки по компонентам - нормально.
  • Источник запроса: задачу поставил Бондаренко для подготовки к аттестации («прикрыть попу»). Оксана говорила, что такого документа ещё не готовили - это первая итерация.

2. Руководство по обновлению и миграции на v2.1

  • Даниил собрал инструкции по обновлению со всех компонентов (Brest, Rubackup, AstroMonitoring, LD Pro и др.) - вопросов по сбору нет.
  • Сценарий «добавление новых компонентов» (SDN, IAM, APIM): решили пока НЕ рассматривать - при переходе с 1.3.1/Brest на 2.1 в любом случае требуется переустановка ОС (новая платформа рядом + миграция данных).
  • Два сценария миграции: (а) с платформы 1.3.1 -> 2.1, (б) с Brest -> платформа 2.1 (через обновление Brest до 4.0.2 + доставка компонентов). Обе задачи должны быть в бэклоге RnD.
  • Илья Устинов начинает тестирование сценария обновления 1.3.1 -> 2.1 по задаче ACP-7297 (инструкции собраны в ACP-6792).
  • Клиенты с Brest 3.3.3: обновление до платформы 2.1 делается руками сопровождения. Клиентов пока мало - «по пальцам пересчитать».
  • FreeIPA -> ALD Pro: Саша Лещев говорил, что «заворачивает» клиентов, у которых Brest + FreeIPA. Причина: нет инструкции миграции FreeIPA -> ALD Pro (платформа = Brest + ALD Pro). RnD должны проверить и описать миграцию. Вопрос обсуждался с Высовым - понятно, в какую сторону копать.
  • ALD -> FreeIPA (обратная): не делаем. Новые установки - сразу с FreeIPA. Существующие клиенты на ALD - аддоном; вряд ли будут мигрировать обратно.
  • Конфликт с клиентами на ALD: если у клиента уже есть ALD как контроллер домена, а платформа требует новый ALD Pro - коммерческий вопрос. Технически: платформенный ALD Pro подключается к доменному ALD клиента как внешний домен и подгружает данные. Вопрос к Александру: как объяснить клиенту ценность.

3. Лицензии компонентов и автоматическая активация

  • Даниил подготовил требования к инсталлятору по работе с лицензиями: автоматическая загрузка и активация в ходе развёртывания.
  • Текущая ситуация: у каждого продукта свой способ получения лицензий - где-то ЛК, где-то через поддержку Sirius. «Квест: пойди туда - не знаю куда, найди лицензию».
  • Прогресс по компонентам:
    • Brest, ОС, AstroMonitoring - есть подписочная модель через ЛК (активация лицензий)
    • Rubackup - должен появиться в ЛК (3 квартал), Кулиничев вышел из отпуска, вопрос подвис
    • BillManager - за скобками
  • Решение: если не рассматривать BillManager, переориентируемся на манифесты - тогда запросов к платформе нет.
  • Александр и Сергей поговорят с Иваном Мешковым по BillManager.

4. Разграничение зон ответственности и взаимодействие с продуктовыми командами

  • Проблема: часть технических вопросов упирается в коммерцию. Сергей обходил все команды - AstroMonitoring («заработали на вас 8 млн, покажите pipeline») и Bill ответили аналогично.
  • Позиция Александра: если компонент не хочет интегрироваться в инсталлятор - ок, не ставим его. Прикрутим Zabbix вместо Astra Monitoring. Но давайте дадим им шанс - «у вас классная штука, сделайте средства, чтобы её можно было ставить в платформу».
  • Эскалация: если Rubackup не готов дорабатываться под платформу - эскалируем в бизнес (к Александру). Основной потребитель Rubackup через платформу - сам Rubackup.
  • Встречи с продуктовыми командами: Сергей + Александр ходят вместе.

5. Резервное копирование платформы

  • Августовский патч: Rubackup сможет бэкапить конфигурацию платформы (Brest VM). Временное решение.
  • Целевое (конец года): бэкап платформы через Brest (модуль Brest VM в Rubackup 3.0).
  • Rubackup 3.0: не будет сертифицирован.
  • Rubackup 2.9: ветка жива, будет сертифицирована, но без поддержки Brest VM. Баги из 2.9 не фиксятся - всё идёт в 3.0.
  • Итог: до конца года нет сертифицированного средства РК для платформы.
  • Бэкап пользовательских данных: возможен через Rubackup (любая версия) или Infoprotect внутри тенанта/VDC клиента. Через API Brest (когда появится) - Rubackup будет отставать ещё на полгода.
  • Нужна встреча с Кулиничевым (Rubackup) - Сергей и Александр сходят вдвоём.
  • Сергей просит Александра пообщаться также с Acronis и Infoprotect по вопросу бэкапа.

6. Процесс приёмки фич командой RnD

  • Проблема (на примере API СРК): фича реализована формально по постановке архитектора, но в проде невалидна. Саша Лещев (RnD) обнаружил постфактум. Корень: архитекторы не связывались с RnD после получения концепта.
  • Решение:
    • Если RnD участвовал в проработке требований к фиче - автоматически участвует в приёмке (демо, не полноценное тестирование).
    • На PBR ТПМ определяет, нужен ли RnD; у Саши Лещева право голоса («ребята, тут вы сами справитесь»).
    • Для критичных фич - блокирующая приёмка: если RnD не пропускает, заворачиваем обратно.
    • Для некритичных (ручки в Bill и т.п.) - не обязательно.
    • Дмитрий Тайлаков пропишет процесс.
  • Людмила: ресурс RnD ограничен - не перегружать.

7. Концептуальный подход к выпуску обновлений с CVE

  • Александр поднял тему: взаимодействие с Департаментом сертификации по подготовке дистрибутивов с CVE. Производство дистрибутивов - на On-prem, документация - на ACP.
  • Решение: отложить до следующей встречи. Александр накинет тему на 20 минут.

Решения

  • Единый список CVE - не делаем. Каждый сертифицированный компонент публикует свой формуляр с CVE при релизе в ЛК. Если появится запрос от заказчика - соберём единое полотно.
  • Сценарий «частичная доставка компонентов» - пока не рассматриваем. Переход на 2.1 = новая платформа рядом + миграция данных.
  • Миграция с Brest -> платформа 2.1 - отдельная задача. Два сценария: (а) 1.3.1 -> 2.1, (б) Brest 3.3.3 -> 2.1 (через 4.0.2 + доставка компонентов).
  • ALD -> FreeIPA (обратная миграция) - не делаем. Новые установки с FreeIPA. Существующие ALD - аддон.
  • Лицензии через манифесты - если не рассматривать BillManager, переориентируемся на манифесты, запросов к платформе нет.
  • Приёмка фич RnD - если RnD участвовал в проработке требований -> автоматически участвует в демо-приёмке. Для критичных фич - блокирующая.
  • Бэкап платформы: целевое - Brest (конец года), промежуточное - Rubackup (августовский патч).

Анализ встречи 2026-07-28

5 главных тем

  1. CVE и документирование - Brest, ALSI, LD Pro. Единый список не нужен: каждый сертифицированный продукт сам публикует формуляр в ЛК.
  2. Миграция на 2.1 - инструкции собраны, сценарий «частичной доставки» отклонён. Два сценария миграции: 1.3.1 -> 2.1 и Brest -> 2.1. Нужна инструкция FreeIPA -> ALD Pro.
  3. Лицензии и инсталлятор - переориентация на манифесты. BillManager под вопросом. Rubackup обещал зайти в ЛК.
  4. Бэкап платформы - сертифицированного решения до конца года нет. Целевое - Brest, промежуточное - Rubackup (август). Нужны переговоры с Rubackup, Acronis, Infoprotect.
  5. Приёмка фич RnD - урок из API СРК: формальная реализация без валидации RnD = провал. Процесс: демо-приёмка для фич, где RnD участвовал в требованиях.

AAR (After-Action Review)

1. Что планировали?

Первый синк ACP ↔ On-prem: синхронизировать ожидания, выявить совместные активности, разграничить зоны ответственности.

2. Что получилось?

Удачно:

  • Закрыт вопрос по списку CVE: не делаем единый список, каждый компонент публикует свой формуляр
  • Зафиксированы два сценария миграции 1.3.1/Brest -> 2.1, дан старт тестированию
  • Поднята и конструктивно разобрана проблема приёмки фич без RnD (кейс API СРК)
  • Александр и Сергей договорились о совместных походах к компонентам
  • Чётко зафиксирован статус по бэкапу: сертифицированного РК до конца года нет

Неудачно:

  • Не хватило времени на тему инсталлятора (разграничение) - ушли в лицензии и бэкап
  • Вопрос лицензирования BillManager отложен
  • Тема «концептуальный подход к CVE» отложена до следующей встречи

3. Почему?

Первая встреча - много тем для синхронизации. Обсуждение бэкапа и лицензий оказалось глубже, чем ожидалось.

4. Что будем делать иначе?

  • Готовить повестку заранее - Сергей признал, что не скинул agenda. На следующий раз - отправлять до встречи.
  • Жёстче держать тайминг - выделять слоты на темы, чтобы успеть всё.
