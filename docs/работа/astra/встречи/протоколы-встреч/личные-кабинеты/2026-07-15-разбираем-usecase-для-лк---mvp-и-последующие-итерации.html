Протокол встречи

Тема: Валидация таблицы use cases ЛК — полнота покрытия BillManager, разбивка по вехам (прототип/1-я итерация/дальше) Участники: @Сергей Склабовский, @Ольга Милащенко, @Максим Югай, @Дмитрий Попенов, @Андрей Иволга, @Александр Шадрин, @Михаил Перевалов

Подготовка: 11-07-2026 приоритеты по доработкам ЛК vs IaaS-оркестратор

Контекст

Сергей подготовил таблицу use cases на основе того, что уже реализовано в BillManager, для проверки: (1) все ли кейсы учтены, (2) что идёт в прототип (MVP), (3) что — в следующие итерации. Встреча 30 мин, плотный обзор.

Ключевые обсуждения

Терминология: API Gateway vs IaaS Orchestrator

  • @Александр Шадрин и @Андрей Иволга синхронизировались: сервис унифицированного API (legacy API Gateway) — это первая версия IaaS Orchestrator, а не отдельная сущность. Решено уйти от термина APIM, называть IaaS Orchestrator.
  • IaaS Orchestrator предоставляет API для ЛК (NewGen).

SSO и вход/выход

  • @Максим Югай: SSO через IAM — в MVP, без него пользователь не попадёт в ЛК.
  • IaaS Orchestrator уже поддерживает OIDC (через IAM).
  • @Ольга Милащенко: сценарий входа/выхода пока не до конца проработан (input points не определены) — не числить готовым.
  • @Максим Югай берёт детализацию в работу.

Виртуальные машины — MVP

  • ЖЦ ВМ: создать из образа, список, изменить конфиг (CPU/RAM), удалить — @Дмитрий Попенов подтвердил: минимально достаточно.
  • Управление питанием (вкл/выкл/перезагрузка) — @Ольга Милащенко заметила отсутствие, @Михаил Перевалов добавит.
  • Терминология: не “инстанс”, а “ВМ”.
  • Шаблоны ВМ — не в MVP, отдельный жизненный цикл.
  • IaaS Orchestrator: переделать создание ВМ без создания промежуточного шаблона (@Александр Шадрин).

Сети — MVP

  • VLAN с предварительной настройкой администратором.
  • Параметры: номер VLAN + адресное пространство.
  • Сетевой интерфейс: 1 интерфейс, 1 адрес для MVP.
  • Терминология: не “прикрепить сеть к ВМ”, а “добавить сетевой интерфейс к ВМ”.

Диски

  • Диск — это persistent-образ в терминах IaaS Orchestrator.
  • В Brest отдельной сущности “диск” нет — есть образы.
  • @Александр Шадрин: IaaS Orchestrator эмулирует логику “диска” через свою БД (создание пустого диска, прикрепление к ВМ).
  • @Дмитрий Попенов: сценарий выглядит воспроизводимым, но нужна проекция на OpenNebula/Brest.
  • Диски — в MVP.

Тенантный контекст

  • MVP — single-tenant, один предсозданный тенант.
  • @Андрей Иволга: пользователь должен видеть, к какому тенанту относится (хотя бы ID/имя).
  • @Михаил Перевалов: отрисовать информацию о тенанте — проблема только получить данные (от IAM).
  • Управление ролями и переключение тенантов — в следующих итерациях (@Максим Югай).

IAM + Brest интеграция

  • @Дмитрий Попенов поднял: интеграция IAM с Brest (проброс пользовательского контекста) — не в MVP.
  • Но @Александр Шадрин: ДИБ (безопасность) требует проброса контекста до Brest. Нужно будет в 1-й итерации после октября.
  • @Ольга Милащенко предложила формализовать требования к интеграции IAM с каждым компонентом платформы.

Мультитенантность (общая архитектура)

  • @Дмитрий Попенов: тенант = группа пользователей + контейнер ресурсов. В Brest тенант — это VDC, но фактически тенантом считается группа пользователей. Нужно определить, как группы пользователей соотносятся с тенантами.
  • @Александр Шадрин: физическая изоляция тенантов по узлам — пока обсуждается.
  • Решено вынести обсуждение мультитенантности (изоляция, квоты, группы) на следующую встречу.

Решения

  • Терминология: APIM -> IaaS Orchestrator (фикс), “инстанс” -> “ВМ”, “прикрепить сеть к ВМ” -> “добавить сетевой интерфейс к ВМ”
  • SSO через IAM — в MVP, подтверждено всеми
  • ЖЦ ВМ (создать из образа, список, изменить, удалить + питание) — в MVP
  • Сети — VLAN с предварительной настройкой, один интерфейс на ВМ — в MVP
  • Диски (persistent-образы) — в MVP, логику поднимает IaaS Orchestrator
  • Тенантный контекст — показывать в MVP (принадлежность), управление и переключение — позже
  • Интеграция IAM + Brest — не в MVP, после октября (требование ДИБ)
  • Следующая встреча — по порталу оператора (ЛК админ), на следующей неделе
  • Таблицу use cases переделать: шапка с вехами (прототип / 1-я итерация / 2-я итерация), готовые кейсы — цветом

Анализ встречи 2026-07-15

5 главных тем

  1. MVP ЛК = минимальный ЖЦ ВМ + сети + диски (IaaS Orchestrator) — состав подтверждён, рамки фиксированы
  2. Терминологический хаос: APIM/API Gateway/IaaS Orchestrator — разобрались, зафиксировали единые названия
  3. SSO и тенантный контекст — в MVP, но shallow — пользователь заходит через IAM и видит свой тенант, без переключения
  4. Дилемма дисков: в Brest нет дисков, есть образы — IaaS Orchestrator эмулирует логику persistent-дисков
  5. Интеграция IAM + Brest отложена, но ДИБ требует — нужно будет в 1-й итерации

AAR

1. Что планировали?

За 30 мин: проверить полноту таблицы use cases ЛК относительно BillManager, разбить по вехам.

2. Что получилось?

Удачно:

  • Состав MVP подтверждён всеми ключевыми участниками
  • Закрыт терминологический спор APIM/IaaS Orchestrator
  • Выявлены missing кейсы (управление питанием ВМ, тенантный контекст)
  • @Дмитрий Попенов поднял архитектурные вопросы по мультитенантности и IAM+Brest

Неудачно:

  • @Ольга Милащенко не успела подготовиться (занята с Прохором)
  • Не успели пройтись по всем use cases (обсуждали только ВМ, сети, диски, SSO)
  • Не успели затронуть портал оператора (админка ЛК)

3. Почему?

  • 30 мин — слишком мало для такой повестки (7 участников, плотный контент)
  • Таблица use cases требует переработки формата (шапка с вехами)

4. Что будем делать иначе?

  • Таблицу привести к единому формату с вехами и маркировкой готовности
  • На встречу по админке ЛК заложить 45-60 мин
  • Ольге давать материалы заранее (за 2 рабочих дня)
