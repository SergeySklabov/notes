ADR-TMS-001Соглашение о тенантах

1. Цели

Обеспечение однозначного маппинга сущностей

  • Гарантировать однозначное соответствие между техническими и бизнес‑сущностями
    • тенант ↔ клиент BILLmanager ↔ услуга ВДЦ ↔ VDC Брест ↔ тенант SDN
  • Фиксация архитектурной модели тенантов (на ближайшие релизы - 2.2 или позднее)
    • Явно зафиксировать и формализовать существующую архитектурную развилку в части модели

2. Контекст принимаемого решения

UPD:

  • Документ не претендует на статус “стандарта”
  • Документ отражает реализацию на ближайшие релизы в текущих условиях (BILLmanager, Брест, SDN и пр.)
  • Документ не описывает как мы придем в целевое состояние

2.1. Пользовательский контекст

Необходимо определить пользовательский (identity) контекст по отношению к сущности тенант (это тема для отдельного ADR, для простоты приму это как допущение). Это важно, потому что существуют разночтения по этому вопросу, например:

тут: ADR-121-001 Функции IAM в платформе как чёрном ящике

в том же ADR:

или тут: Соглашение об определениях в системе управления требованиями

или тут: Модель предметной области Версия 0.2

Наличие таких связей и формулировок в материалах означает, что:

  • пользователь (его учетная запись) существует в рамках тенанта, она не может существовать отдельно
  • сначала появляется тенант → потом учетная запись пользователя, удаление тенанта → удаление ресурсов и учетных данных
  • тенант является изолированным контейнером учетных данных (тенантные политики аутентификации, приложения, роли, импорт учетных данных из внешних IdP в конкретный тенант, федерации и трасты на уровне тенанта и т.д.)
    • пример, тенант Microsoft Azure = Entra (облачный каталог Active Directory, ресурсы “живут” в subscription)
      • пример, тенант AWS = Account (каталог учетных данных + ресурсов)

Очевидно, это сильно отличается от нашей текущей реализации, где IAM - централизованный. Другими словами, у нас:

  • тенант не является контейнером с учетными данными
  • тенант имеет ресурсно-центричную модель (VDC, группа ВМ, группа сетей и пр.)
  • доступ к тенантным ресурсами организуется через роли (доступ - это “user_id, role=tenant_admin, scope=tenant_id”)

Простыми словами у нас развилка:

  • тенант = пользователи + ресурсы, или
  • тенант = ресурсы (наш кейс на ТЕКУЩИЙ МОМЕНТ)

Эту тему стоило бы разобрать отдельно, в рамках текущего ADR принимаю допущение, что тенант на текущий момент - это только про ресурсы. Нужно подтвердить.

UPD:

2.2. Общая модель

Целевая модель предполагает возможность создания множества тенантов, которые сходятся в корне каталога тенантов. Для каждого потребителя предполагается отдельное “дерево” тенантов. Учетные данные и роли хранятся в платформенном IAM (это дельный рилм, однако все потребители живут вместе в этом рилме). Сущность “организация” (корень каталога тенантов) мы выносим за скобки, однако мы вынуждены иметь проекции этого корня. Описано ниже.

2.3. Прочие допущения

На текущем этапе приняты следующие допущения:

  • источником истины состояния тенанта является компонент Tenant Mgmt
  • 1 потребитель (организация/юр.лицо) может иметь N тенантов
  • пользовательским интерфейсом для управления тенантом выступает BILLmanager
  • предполагается доступ пользователя в разные тенанты с разными ролями (пока определили tenant_owner)
  • в текущей реализации BILLmanager только Клиент может иметь лицевой счет (договор на услуги)

3. Предлагаемое решение

3.1. Вариант 1

Текущая реализация (в ACP 1.3, 2.0)

Ключевые положения:

  • тенант = 1 услуга ВДЦ = 1 VDC Бреста
  • потребитель в рамках клиента может заказывать N услуг ВДЦ (N VDC в Бресте) → потребитель может иметь N тенантов

3.2. Вариант 2

Вариант предлагался Дмитрием Пронюшкиным и рассматривался в рамках ADR-OPP-001 Создание клиента на Портале оператора

Ключевые положения:

  • тенант = 1 клиент BILLm = 1 услуга ВДЦ = 1 VDC Бреста = 1 тенант SDN
  • потребитель может иметь 1 клиента в BILLm → потребитель может иметь 1 тенант
  • потребитель может заказать 1 услугу ВДЦ (или она заказывается автоматически при создании клиента)

Технические ограничения:

  • потребитель ограничен 1 тенантом
  • отсутствует возможность гранулярного квотирования ресурсов (фактически есть одна квота на клиента / ВДЦ)
  • отсутствует возможность выбора нужного “железа” для размещения ресурсов (определяется тарифным планом в BILLm при заказе ВДЦ)
  • все виртуальные ресурсы в рамках VDC расположены в одной сети SDN → для разграничения сетевой видимости необходимо использовать внешние средства (FW)

ИТОГ: НЕ ПОДХОДИТ, ОЧЕНЬ МНОГО ОГРАНИЧЕНИЙ

Возможность потребителя иметь N тенантов (N клиентов BILLm) описана в варианте 4 ниже

3.3. Вариант 3

Вариант рассматривался в рамках того же ADR-OPP-001 Создание клиента на Портале оператора в качестве альтернативной реализации

Ключевые положения:

  • тенант = 1 клиент BILLm = N услуг ВДЦ = N VDC Бреста = 1 тенант SDN
  • потребитель может иметь 1 клиента в BILLm → потребитель может иметь 1 тенант
  • потребитель может заказать N услуг ВДЦ

Технические ограничения:

  • потребитель ограничен 1 тенантом
  • все виртуальные ресурсы в рамках VDC расположены в одной сети SDN → для разграничения сетевой видимости необходимо использовать внешние средства (FW)

ИТОГ: НЕ ПОДХОДИТ, ФАКТИЧЕСКИ ПОТРЕБИТЕЛЬ ОГРАНИЧЕН 1 ТЕНАНТОМ

3.4. Вариант 4

1 потребитель = N клиентов N VDC

Тенант как сущность облачной платформы однозначно сопоставляется с Клиентом BILLmanager. При этом сохраняется возможность открытия лицевого счета на уровне Клиента.

Ключевые положения:

  • тенант = 1 клиент BILLm = N услуг ВДЦ = N VDC Бреста = 1 тенант SDN
  • потребитель может иметь N клиентов в BILLm → потребитель может иметь N тенантов
  • потребитель может заказать N услуг ВДЦ

Технические ограничения:

  • такой подход “ломает” архитектурный фундамент BILLm (ходил за консультацией в Билл)
    • BILLm однозначно определяет клиента по пользователю
      • придется переписывать всю логику идентификации клиента и авторизацию пользователей
  • все виртуальные ресурсы в рамках VDC расположены в одной сети SDN → для разграничения сетевой видимости необходимо использовать внешние средства (FW)

ИТОГ: НЕ ПОДХОДИТ, АРХИТЕКТУРНЫЕ ОГРАНИЧЕНИЯ БИЛЛА

В рамках предлагаемого решения:

  • проекция тенанта в BILLmanager - Клиент (если потребитель имеет N тенантов = потребитель имеет N Клиентов)
  • Клиент создается оператором платформы вручную по заявке пользователя (текущая реализация: оператор создает в ALD орг. юнит и учетные записи в нем, которые импортируются по LDAP как Клиенты и его пользователи)
    • BILLmanager → Tenant mgmt: создание тенанта и получение идентификатора (tenant_id)
      • BILLmanager → ALD (API/LDAP): создание группы и УЗ администратора тенанта
      • BILLmanager → IAM (API): создание области (tenant_id) и назначение роли
      • BILLmanager → SDN (API): создание тенанта SDN
      • BILLmanager → создает Клиента

Что нужно доработать:

  • BILLmanager: механизм создания/импорта Клиентов из каталога ALD нужно переделать (с OU на группы)
  • BILLmanager: потребуется поддержка SSO с платформенным IAM
  • BILLmanager: (вероятно) потребуется доработка механизма авторизации
  • BILLmanager: потребуется интеграция с IAM в части назначения роли (tenant_owner, tenant_admin) и создания области (tenant_id)
  • BILLmanager: потребуется интеграция с SDN (создание/удаление тенанта)
  • IAM: потребуется реализация базовой модели управления доступом на основе ролей (tenant_owner, tenant_admin + назначение области tenant_id)
  • IAM: потребуется реализация возможности управления ролями (в текущем релизе отсутствует)
  • Интеграция BILLmanager → SDN: интеграция через IAM для авторизации API (M2M, BILLmanager получает токен в IAM для доступа к API SDN)
  • Интеграция BILLmanager → Брест: интеграция через IAM для авторизации API (M2M, BILLmanager получает токен в IAM для доступа к API Брест)

3.5. Вариант 5

Обсуждался на последней встрече с Дмитрием Пронюшкиным

Ключевые положения:

  • все потребители используют технологического клиента BILLm
  • тенант как сущность является дополнительным идентификатором для услуги ВДЦ
  • тенант = 1 услуга ВДЦ = 1 VDC Бреста = 1 тенант SDN
  • потребитель может заказывать N услуг ВДЦ, Билл маркирует их tenant_id
  • сохраняется возможность квотирования ресурсов на уровне тенанта (ВДЦ)

Технические ограничения:

  • такой подход полностью лишает потребителя функций биллинга
    • все пользователи принадлежат единственному технологическому клиенту
  • нужно будет “учить” BILLmanager различать какой тенант кому пренадлежит
    • при создании нового тенанта нужно собирать роль в Билле и применять при авторизации пользователя
      • role=tenant_owner - scope=tenant_id
  • фактически реализуется модель “куча пользователей” → “куча ресурсов”, а задача доступа решается ролями

Что нужно доработать:

  • BILLmanager: потребуется поддержка SSO с платформенным IAM
  • BILLmanager: потребуется доработка механизма авторизации
  • TMS: потребуется интеграция с IAM в части назначения роли (tenant_owner, tenant_admin) и создания области (tenant_id)
  • BILLmanager: потребуется интеграция с SDN (создание/удаление тенанта)
  • IAM: потребуется реализация базовой модели управления доступом на основе ролей (tenant_owner + назначение области tenant_id)
  • IAM: потребуется реализация возможности управления ролями (в текущем релизе отсутствует)
  • Интеграция BILLmanager → SDN: интеграция через IAM для авторизации API (M2M, BILLmanager получает токен в IAM для доступа к API SDN)
  • Интеграция BILLmanager → Брест: интеграция через IAM для авторизации API (M2M, BILLmanager получает токен в IAM для доступа к API Брест)

3.6. Вариант 6

Ключевые положения:

  • фактически является усовершенствованной версией варианта 1
  • внутри Билла возникает tenant_id, который однозначно связан с услугой ВДЦ
  • можно отдельно рассмотреть вариант, что в рамках тенанта можно иметь N услуг ВДЦ, но это усложнит реализацию, не изменяя при этом общий принцип
  • тенант = 1 услуга ВДЦ = 1 VDC Бреста = 1 тенант SDN
  • потребитель в рамках клиента может заказывать N услуг ВДЦ (N VDC в Бресте) → потребитель может иметь N тенантов
  • сохраняется возможность квотирования ресурсов (per tenant = per VDC)
  • сохраняется возможность использования функций Биллинга
  • сейчас в Билле проектируется аналогичный компонент - ПРОЕКТ, фактически это аналог того, что мы сейчас именуем тенантом

Что нужно доработать:

  • BILLmanager: потребуется поддержка SSO с платформенным IAM
  • BILLmanager: потребуется доработка механизма авторизации
    • авторизация по tenant_id (спорно)
  • TMS: потребуется интеграция с IAM в части назначения роли (tenant_owner, tenant_admin) и создания области (tenant_id)
  • BILLmanager: потребуется интеграция с SDN (создание/удаление тенанта)
  • IAM: потребуется реализация базовой модели управления доступом на основе ролей (tenant_owner + назначение области tenant_id)
  • IAM: потребуется реализация возможности управления ролями (в текущем релизе отсутствует)
  • Интеграция BILLmanager → SDN: интеграция через IAM для авторизации API (M2M, BILLmanager получает токен в IAM для доступа к API SDN)
  • Интеграция BILLmanager → Брест: интеграция через IAM для авторизации API (M2M, BILLmanager получает токен в IAM для доступа к API Брест)

4. Послесловие

Какие есть мысли:

  • Нужно четко зафиксировать границы тенанта как сущности облачной платформы
    • тенант = только ресурсы
      • тенант = ресурсы + учетки
  • То, что мы не делаем компонент Org Management в рамках платформы, не избавляет нас от необходимости создавать его проекции в других компонентах (например, IAM, SDN)
    • Это необходимо, чтобы однозначно сопоставить пользователя и потребителя
      • Без этого сложно реализовать функции самообслуживания (IAM не знает какие учетные данные связаны с потребителем, есть только связь “пользователь - тенант”, а пользователи могут от разных потребителей)
      • Без этого невозможно биллить клиента по организации
      • Без этого крайне сложно реализовать авторизацию в Билле (в Билл приходит пользователь конкретного клиента, очевидно, что проще передать организационный контекст авторизации)
  • Попытки транспонировать сущности BILLm (отнести Клиента к Тенанту) проводят к нарушению связей с целевой моделью
    • Невозможно организовать доступ между Клиентами, это архитектурное ограничение Билла
