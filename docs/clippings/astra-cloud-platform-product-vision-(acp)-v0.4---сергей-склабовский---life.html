1. Введение

Данный документ представляет собой продуктовое видение облачной платформы - Astra Cloud Platform (ACP) и сопутствующих услуг. Разработка ACP имеет целью создание продукта, способного эффективно конкурировать с ведущими российскими и мировыми игроками рынка облачных технологий предоставляя функционально полное и гибкое решение для корпоративных клиентов.Разработка планируется в рамках экосистемы продуктов ГК Астра и предполагает возможность расширения и унификации портфеля продуктов и сервисов.

Документ для внутреннего использования в ГК Астра, предназначен для руководителей разного уровня, разработчиков компонентов платформы, аналитиков, архитекторов.

Документ будет использован для:

  • постановки целей команды ACP/(AIC) и планировании;
  • принятии решений и оценке их соответствия следования основной стратегии продукта;
  • понимания участниками целей бизнеса;
  • управления ожиданиями.

1.1. Определение платформы

Astra Cloud Platform - это единое ядро для масштабируемого и управляемого предоставления облачных продуктов нашим конечным клиентам.

Под облачными продуктами понимаются как решения из продуктового портфеля ГК Астра, так и продукты пратнеров.

Способ предоставления решения в качестве SaaS/PaaS Платформы или через XaaS - будет определятся индивидуально.

1.2. Цели создание платформы

Создание Astra Cloud Platform несет в себе следующие цели:

  • Монентизация виртуальных ресурсов за счет предоставления качественных сервисов, как самой виртуализации, так и IaaS/PaaS/SaaS в том числе за счет сервисов из ГК Астра и партнерских решений, обеспечивая при этом должный уровень маржинальности
  • Монетизации осуществляется за счет четырёх моделях поставки:
    • public (как сервис из облака)
    • on-prem (как продукт в контур клиента),
    • hybrid (единое управление обеими моделями) и
    • multi-cloud (управление нашими и сторонними облаками через единый API)
  • Создание комплементарных фундаментальных сервисов облака (такие как IAM, Monitoring, Logging, Audit, Resource Manager, etc.), становящихся общим основанием для всех облачных продуктов и исключающих дублирование функциональности
  • Унификация процесса добавления новых компонентов платформы и сокращение time-to-market для новых продуктов за счёт готовых интеграций, общепринятых паттернов и переиспользуемых шаболнов (привет Dev Platform:)
  • Обеспечение гарантированного уровня надёжности (SLA) и прозрачности состояния сервисов для клиентов.
  • Автоматизация процессов компании, связанных с предоставлением клиентам облачных продуктов, а также сокращение ручных операций и времени вывода продукта
  • Предоставление клиентам механизмов самообслуживания
  • Реализация общих для всех продуктов механик: регистрация клиента, заказ продуктов и управление, тарификация и выставление счетов
  • Обеспечение технологической независимости за счет возможности смены продуктов (OpenNebula, Боцман и др.) без изменения клиентского API и бизнес-логики.

2. Возможности платформы

Платформа предоставляет наборы возможностей, которые можно разделить на платформенными и функциональными.

  • Платформенные сервисы предоставляют свои функции какв интересах пользователей, так и в интересах функциональных сервисов;
  • Функциональные сервисы предоставляют свои функции как в интересах пользователей, так и в интересах других функциональных сервисов.

Платформенные сервисы включают в себя ряд возможностей фундаментальных сервисов облака (такие[как IAM, Monitoring, Logging, Audit, Resource Manager, etc.), становящихся общим основанием для всех облачных продуктов. Это позволит

  • обеспечить технологической независимости за счет того, что вся бизнес-логика сосредоточена в платформенных сервисах, что даст возможность замены продуктов (OpenNebula, Боцман и др.)
  • уменьшение затрат при добавление новых компонентов/дополнительной ценности платформы

Это достигается за счет соблюдения платформенного принципа: каждая компонента делает ровно одну целевую вещь и делегирует смежные задачи смежным компонентами (например через брокер или API Gateway) т.е. компонента не может выполнять работу, которая относится к другой компоненте, даже если «так проще»

Примеры нарушений и правильных границ:

Пример 1

Некорректно: Биллинг сам проверяет, есть ли у клиента доступ к услуге.

Правильно:

    • Billing меняет статус клиента/проекта (например, «заблокирован за неуплату») и передаёт событие в Tenant Management;
      • Tenant Management обновляет статус проекта;
      • IAM при следующей попытке доступа проверяет статус проекта и отклоняет запрос (или API Gateway блокирует на основе данных от IAM).

Пример 2

Некорректно: Оркестратор сам считает потребление и пишет в биллинг.

Правильно: Оркестратор создал ресурс, отдал событие в брокер. Учёт потребления (Metering) подхватил и начал собирать метрики.

Пример 3

Некорректно: Система инцидентов сама пишет в чат клиенту.
Правильно: Система инцидентов передаёт статус в Коммуникации (Notifications), те отправляют уведомление.

2.1. Платформенные сервисы

2.1.1. Блоки компонент

2.1.1.1. Пользовательский слой / интерфейсы

Это не отдельный блок, а точка входа. Компоненты здесь не содержат бизнес-логики, а только маршрутизируют запросы и отображают данные.

Компонент 0.1. Личный кабинет (UI)

  • Что делает: предоставляет веб-интерфейс для клиентов: управление проектами, заказ услуг, просмотр счетов, мониторинг ресурсов;
  • Границы: не содержит бизнес-логики. Только отрисовка UI и вызов API. Не хранит состояние;
  • Зависит от: Внешнее API.

Компонент 0.2. Внешнее API (Public API)

  • Что делает: публичный API для автоматизации: Terraform, CLI, интеграции партнёров. Принимает запросы, аутентифицирует, маршрутизирует в сервисы;
  • Границы: не содержит бизнес-логики. Только маршрутизация и базовая валидация. Не хранит состояние;
  • Зависит от: IAM (аутентификация), все сервисы блоков 1, 2, 3.

2.1.1.2. Блок 1. Управление услугами (OSS/Service Control Plane)

Задача блока - технически предоставить пользователям сервисы/ресурсы исходя из предусловий (наличие/отсутствие необходимых доступов/квот)

Компонент 1.1. Учёт клиентов и доступ (User Managment/IAM)

  • Что делает: хранит пользователей, группы, сервисные аккаунты. Управляет аутентификацией (кто) и авторизацией (что можно). Проверяет доступ к проектам и права на действия;
  • Границы: не знает про квоты, не знает про деньги, не хранит ресурсы. Только идентификация и разрешения;
  • Зависит от: компонент 1.3 (Resource Manager) для проверки существования проекта.

Компонент 1.2. Управление проектами (Tenant Management)

  • Что делает: управляет жизненным циклом проектов/тенантов: создание, блокировка (при долгах), удаление. Обеспечивает изоляцию между проектами;
  • Границы: не хранит ресурсы внутри проекта. Не управляет доступом (это IAM). Только оболочка проекта;
  • Зависит от: компонент 1.3 (Resource Manager), компонент 2.4 (Billing) для блокировки при долгах.

Компонент 1.3. Инвентаризация ресурсов (Resource Manager)

  • Что делает: единый источник правды о всех ресурсах платформы: VM, кластеры, диски, сети, бэкапы. Хранит состояние, отношения, теги, метаданные;
  • Границы: не хранит метрики потребления (CPU сейчас). Не знает тарифы. Только факт существования и атрибуты;
  • Зависит от: компонент 1.7 (Orchestration) получает события создания/удаления, компонент 1.1 (IAM) для проверки доступа к ресурсам.

Компонент 1.4. Каталог услуг (Service Catalog)

  • Что делает: хранит описание всех услуг: VM, k8s, Backup, S3. Для каждой услуги: параметры, допустимые действия,привязка к тарифам, ограничения. Проверяет доступность услуги для проекта;
  • Границы: не знает про квоты и лимиты. Не хранит состояние ресурсов. Только мета-информация об услугах;
  • Зависит от: компонент 1.2 (Tenant Management) чтобы знать, какие услуги включены проекту.

Компонент 1.5. Квоты и лимиты (Quota)

  • Что делает: хранит лимиты по проектам: максимум vCPU, RAM, дисков, количества ресурсов. Проверяет при создании, не превышен ли лимит;
  • Границы: не знает про деньги. Не знает про доступ. Только числа и лимиты;
  • Зависит от: компонент 1.3 (Resource Manager) для получения текущего потребления, компонент 1.2 (Tenant Management) для привязки к проекту.

Компонент 1.6. Управление жизненным циклом услуги (Service Lifecycle Manager)

  • Что делает: управляет состояниями услуги: активна, приостановлена, удалена, в ошибке. Обрабатывает сложные переходы (пауза - возобновление);
  • Границы: часть Orchestration или отдельный слой над ним. Не работает напрямую с провайдерами;
  • Зависит от: компонент 1.7 (Orchestration), компонент 1.3 (Resource Manager), компонент 2.4 (Billing) при паузе.

Компонент 1.7. Оркестратор выполнения (Orchestration)

  • Что делает: единый движок workflow для всех операций: создать, изменить, удалить, приостановить. Управляет последовательностью шагов, повторами, откатами. Не знает, как именно создать VM — вызывает провайдеров;
  • Границы: не содержит логики конкретных технологий. Только координация;
  • Зависит от: все провайдеры (компонент 1.9), компонент 1.3 (Resource Manager) для обновления статуса, компонент 3.5 (Audit), компонент 3.6 (Notifications).

Компонент 1.8. Внутреннее API (Internal API)

  • Что делает: API для взаимодействия между микросервисами платформы. Обеспечивает единую точку доступа и observability;
  • Границы: доступно только внутри платформы. Не публичное;
  • Зависит от: все сервисы (как потребитель и как провайдер).

Компонент 1.9. Исполнители (Providers/Connector)

  • Что делает: набор драйверов для конкретных технологий: OpenNebula Provider, Боцман Provider, S3 Provider, Backup Provider. Реализуют интерфейс « создать/удалить/обновить » для своего типа ресурса;
  • Границы: не знают про бизнес-логику, клиентов, квоты. Только техническое исполнение;
  • Зависит от: внешние API (OpenNebula, Боцман и т.д.).

2.1.1.3. Блок 2. Коммерция (BSS/Commerce Plane)

Задача блока - монетизировать предоставляемые сервисы/услуги, корректно их обсчитав в сторону пользователя

Компонент 2.1. Управление клиентами (CRM / Customer Management)

  • Что делает: хранит данные о клиентах: юридические лица, контакты, договоры, платёжные реквизиты. Управляет статусом клиента (активен, заблокирован);
  • Границы: не знает про ресурсы и потребление. Только информация о клиенте;
  • Зависит от: компонент 1.2 (Tenant Management) для связи клиент → проекты.

Компонент 2.2. Тарифы (Pricing)

  • Что делает: хранит тарифные правила: почасовая оплата, фиксированная плата, промокоды, скидки, пакеты услуг. Отвечает на вопрос «сколько стоит ресурс X в проекте Y»;
  • Границы: не знает, сколько потребил конкретный ресурс. Только правила расчёта;
  • Зависит от: компонент 1.4 (Service Catalog) для привязки тарифов к услугам.

Компонент 2.3. Учёт потребления (Usage)

  • Что делает: собирает метрики потребления от провайдеров и мониторинга. Агрегирует в единицы для биллинга: CPU-часы, GB-часы, количество запросов. Передаёт агрегаты в Billing;
  • Границы: не хранит тарифы. Не списывает деньги. Только учёт потребления;
  • Зависит от: компонент 1.3 (Resource Manager) чтобы понять, какому проекту принадлежит ресурс, компонент 3.1 (Platform Observability) как источник метрик.

Компонент 2.4. Биллинг (Billing )

  • Что делает: получает агрегированное потребление от Metering, применяет тарифы из Tariff & Pricing, списывает с баланса или выставляет счёт. Управляет холдированием, начислениями, платежами;
  • Границы: не хранит метрики потребления. Не знает, как устроена услуга внутри;
  • Зависит от: компонент 2.3 (Metering), компонент 2.2 (Tariff & Pricing), компонент 2.1 (CRM) для реквизитов, компонент 3.5 (Audit).

Компонент 2.5. Лицензирование (Licensing) - возможно отказаться т.к. продажа лицензий строиться больше “ппо-джентльменски”

  • Что делает: управляет лицензиями для on-prem поставок: генерация ключей, проверка при активации, ограничение по количеству сокетов/ВМ/пользователей;
  • Границы: не участвует в public-биллинге. Только для on-prem;
  • Зависит от: компонент 2.1 (CRM) кому выдана лицензия, компонент 1.7 (Orchestration Engine) для проверки при создании.

Компонент 2.6. Аналитика и отчёты (Analytics & Dashboards)

  • Что делает: готовит отчёты для клиентов (детализация расходов, прогнозы) и для внутренних команд (выручка, маржинальность, тренды);
  • Границы: только чтение данных из других сервисов. Не влияет на операции;
  • Зависит от: компонент 2.3 (Metering), компонент 2.4 (Billing), компонент 2.1 (CRM), компонент 1.3 (Resource Manager).

2.1.1.4. Блок 3. Надёжность (Reliability Plane)

Задача блока - обеспечивать стабильность, наблюдаемость и соответствие SLA. Быстро обнаруживать проблемы и реагировать на них.

Компонент 3.1. Наблюдаемость платформы (Platform Observability)

  • Что делает: собирает метрики, логи, трейсы со всех компонент платформы. Хранит, индексирует, визуализирует для SRE и инженеров;
  • Границы: только сбор и хранение. Не анализирует и не алертит (это Alerting);
  • Зависит от: все компоненты платформы как источники данных.

Компонент 3.2. Наблюдаемость для клиента (Customer Observability)

  • Что делает: предоставляет клиенту метрики и логи его ресурсов с фильтрацией по tenant. Отдаёт через API и UI;
  • Границы: не показывает данные других клиентов. Не даёт доступа к платформенным метрикам;
  • Зависит от: компонент 3.1 (Platform Observability) как источник, компонент 1.1 (IAM) для фильтрации.

Компонент 3.3. Алертинг (Alerting)

  • Что делает: анализирует метрики и логи по правилам. При превышении порогов отправляет алерты в Incident Management или дежурным;
  • Границы: только генерация алертов. Не управляет людьми и эскалацией;
  • Зависит от: компонент 3.1 (Platform Observability).

Компонент 3.4. Управление инцидентами (Incident Management)

  • Что делает: получает алерты, группирует в инциденты, определяет приоритет и масштаб. Управляет эскалацией, ведёт таймеры (время до реакции, до восстановления). Фиксирует хронологию;
  • Границы: не исправляет проблему. Только координирует процесс;
  • Зависит от: компонент 3.3 (Alerting), компонент 1.3 (Resource Manager) чтобы понять, кого затронуло, компонент 3.6 (Notifications).

Компонент 3.5. Аудит (Audit)

  • Что делает: логирует все значимые действия: кто, когда, что сделал, с каким ресурсом, успешно или нет. Хранит в неизменяемом виде;
  • Границы: не влияет на операцию. Только запись;
  • Зависит от: все компоненты вызывают при действиях.

Компонент 3.6. Уведомления (Notifications)

  • Что делает: отправляет уведомления клиентам (email, SMS, webhook) и дежурным (MAX, что-то пока еще не запрещенное) о событиях: создание ресурса, инцидент, плановые работы;
  • Границы: только доставка сообщений. Не формирует содержание (получает готовое);
  • Зависит от: компонент 1.7 (Orchestration Engine), компонент 3.4 (Incident Management), компонент 2.1 (CRM) для контактов.

Компонент 3.9. Платформенным бэкап (Platform Backup)

  • Что делает: регулярно создаёт бэкапы состояния платформы: базы данных, конфигурации, метаданные. Обеспечивает восстановление после катастроф.
  • Границы: не касается клиентских данных. Только состояние самой платформы.
  • Зависит от: компонент 1.3 (Resource Manager), компонент 1.1 (IAM), компонент 2.4 (Billing) как источники данных для бэкапа.

Комментарии:

  • Компоненты и их границы условны и преследуют цель зафиксировать набор возможностей. Физически же несколько компонент могут быть реализованы в рамках одного решения/продукта при соблюдении условий из п. 2.1.2;
  • Провайдер/коннектов для бэкапа (компонент 1.9) — это драйвер, который выполняет команды, а Платформенный бэкап (3.7) — это сервис, который управляет политиками и расписанием бэкапов;
    • Подарзумевается, что для каждого сервиса сервиса будет свой провайдер/коннектор.
  • Observability и Audit могут быделены не в компоненты, а в “сквозные функции” - слои, пронизывающие все блоки, а не в рамках отдельного блока наряду с блоками 1,2 и 3, но кажется это вопрос терминологий;
  • Не забыть потом дописать про Регионы, Зоны доступности, Федерации (это прям уровень 4).

2.1.2. Решения/продукты на базе которого будет реализованы компонент

Для каждого конкретного компонента и каждого конкретного случая выбор решения/продукта должен быть индивидуальным

Основные критерии, которые должны выполнятся при выборе и реализации компонентов:

  • Сохранения технологической независимости - должна остаться возможность смены продуктов (OpenNebula, Боцман и др.) без изменения клиентского API и бизнес-логики;
  • Сохранятся минимальные затраты на добавление новых компонентов платформа;
  • В случае, если рассматривается решение из продуктового периметра ГК Астра, то продукт должен из коробки обладать набором возможностей, соотвествующим границам компонента или иметь в своей дородной карте требуемые платформе возможности в удобоваримые сроки:
    • Тут должно соблюдаться условие, что платформенные сервисы являются фундаментальными сервисами и исключают дублирование функциональности;
    • Принятие решения по исключению применения продукта из платформенных сервисов не исключает его использования в качестве функицональных. Например, RuBackup может не стать платформенным бэкапом, но стать backup-as-a-service
  • В случае если решение из продуктового периметра ГК Астра не удовлетворяет условиям - рассматриваем альтернативные решения

2.1.3. Переиспользование текущих наработок и изменения их для соотвествия текущему видению

В целях обеспечения последовательного и непрерывного перехода к целевому состоянию предлагаются следующие шаги:

  1. Зафиксировать baseline. Согласовать состояние as - is по всем, указанным в п. 1. артефактам. Дооформить отсутствующие артефакты при необходимости, если выяснится в процессе согласования
  2. Выполнить оценку влияния нового Видения
    • Согласовать изменения глоссария;
      • Согласовать изменения Контекста;
      • Согласовать изменения Контейнеров;
      • Согласовать изменения Компонентов;
      • Согласовать изменения Информационной модели (сущности, их связи и словари);
      • Согласовать изменения Карты вариантов использования;
      • Согласовать изменения Ролевой модели;
      • Выделить и приоритизировать пользовательские требования для актуализации/разработки;
      • Актуализировать/Разработать и согласовать новые варианты использования в соответствии с приоритетами;
      • Актуализировать/Разработать новые спецификации ФТ, НФТ,API в соответствии с приоритетными пользовательскими требованиями.

2.1.4. Cookbook для добавления новых сервисов

Добавление новых сервисов (в первую очередь фунцикаиональных) должно осуществляться с минимальным привлечением команды Облачной Платформы. Для этого должны быть подготовлены наборы артефактов и инструментов, включающих:

  • Описание доменной модели платформенных сервисов;
  • Описание API
  • Преднастроенный Swagger UI
  • список будет корректироваться и дополнятся

При этом как показывает практика (на примере коллег из Cloud.ru) всеобъемлющая документация не является драйвером быстрого и безболезненного добавления нового сервиса - всё-равно нужно группа специалистов, которые проведут команды с их продуктами happy path’ом по добавлению в Платформу.
