### Общий принцип разделения

1. **Платформа не знает внутренностей компонента.** Она работает с ним как с «чёрным ящиком» через контракт (API + метрики + healthcheck).
2. **Продуктовая команда владеет качеством своего компонента** (включая правильность реализации API, корректность перехода статусов, документацию метрик).
3. **Платформа отвечает за**:
    - Базовую наблюдаемость (доступность API, latency, ошибки 5xx).
    - Оркестрацию вызовов (rety, timeout, circuit breaker).
    - Аудит на уровне операций платформы (кто, когда, что).
    - Обеспечение инфраструктурных ресурсов (CPU, RAM, сеть, диски) для самого компонента (если он работает на платформе).
4. **Продуктовая команда отвечает за**:
    - Свои внутренние метрики и алерты (связанные с бизнес-логикой).
    - Логирование своих ошибок.
    - Внутреннее восстановление после сбоев.
    - Своевременное обновление компонента для закрытия уязвимостей и исправления багов.
5. **Эскалация:** дежурный по платформе сначала проверяет, не проблема ли это инфраструктуры (сеть, диски, узлы). Если нет – эскалирует в продуктовую команду с предоставлением всех доступных данных (логов платформы, метрик доступности). Продуктовая команда обязана иметь дежурных в рабочие часы (или 24/7 для критичных сервисов, прописывается в SLA компонента).

| Зона             | Платформа (команда платформенных сервисов)                                                         | Продуктовая команда компонента (BillManager, Bootsman, etc.)                                              |
| ---------------- | -------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------- |
| **Что отвечает** | Инфраструктура, оркестрация, наблюдаемость, безопасность, учёт, биллинг, доступность API платформы | Логика работы компоненты, его внутреннее состояние, обновления версий, исправление ошибок доменной логики |
| **Граница**      | Внешний API компонента (контракт: создать/удалить/обновить, вернуть статус)                        | Внутренняя реализация, специфичные метрики, работа с внешними системами (OpenNebula, Ceph и т.д.)         |

### Разделение по фазам жизненного цикла

#### **А. Интеграция компонента в платформу**

| Действие                                                                                      | Платформа                                  | Продуктовая команда                    |
| --------------------------------------------------------------------------------------------- | ------------------------------------------ | -------------------------------------- |
| Определение API-контракта (create/update/delete/get status)                                   | согласовывает требования к интерфейсу      | предоставляет спецификацию и реализует |
| Разработка оркестратора компоненты                                                            | пишет код, который вызывает API компонента | только даёт консультации               |
| Настройка мониторинга и алертов (базовых: доступность API, latency, errors)                   | +                                          | -                                      |
| Настройка специфичных метрик и алертов (например, «в кластере K8s более 90% подов не готовы») | -                                          | предоставляет метрики или дашборды     |
| Настройка аудита (регистрация факта создания/удаления ресурса в платформенном аудите)         | +                                          | -                                      |
| Определение квот и тарифов для услуги                                                         | + <br>вместе с продуктом                   | -<br>даёт консультации                 |
#### **Эксплуатация (штатный режим)**

| Область ответственности                                                                                           | Платформа                                                  | Продуктовая команда                               |
| ----------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------- | ------------------------------------------------- |
| **Доступность API платформы** (общий API Gateway, авторизация)                                                    | +                                                          | -                                                 |
| **Оркестрация операций** (приём запроса, проверка IAM/Quota/Billing, вызов провайдера, повтор при ошибках, откат) | +                                                          | -                                                 |
| **Создание/удаление ресурса через API компонента** (вызов по контракту, получение ответа)                         | +<br>через оркестратор                                     | +<br>должен корректно отвечать                    |
| **Внутреннее состояние компонента** (его БД, поды, конфигурации)                                                  | -                                                          | +                                                 |
| **Мониторинг доступности компонента** (healthcheck)                                                               | +<br>проверка, что API компонента отвечает 200 OK)         | +<br>должен предоставить эндпоинт                 |
| **Мониторинг специфичных метрик** (количество кластеров, статус подов, версия K8s)                                | -                                                          | +<br>экспортирует метрики                         |
| **Логирование событий компонента** в случае поставки в редакции без системы мониторинга                           | -                                                          | +                                                 |
| **Аудит платформенных контуров** (кто создал кластер, когда)                                                      | +<br>хранит факт создания)                                 | -                                                 |
| **Безопасность (обновления ОС, изоляция сети, TLS на API)**                                                       | +<br>платформа обеспечивает инфраструктурную безопасность) | +<br>безопасность конфигурации самого компонента) |
### Разделение при инцидентах (что-то пошло не так)

#### **Пример инцидента: Запрос на примере Bootsman  на создание кластера завершился ошибкой (таймаут)**

|Шаг|Действие|Кто отвечает|
|---|---|---|
|1|Пользователь через UI платформы создаёт кластер|—|
|2|Платформа проверяет IAM/Quota/Billing – всё ОК|Платформа|
|3|Оркестратор вызывает провайдер → провайдер вызывает API Боцмана|Платформа|
|4|API Боцмана не отвечает в течение 30 секунд (таймаут)|Продуктовая команда (Боцман)|
|5|Оркестратор повторяет вызов 3 раза с экспоненциальной задержкой (политика ретраев)|Платформа|
|6|Все попытки неудачны, оркестратор помечает операцию как FAILED, возвращает клиенту ошибку, пишет в аудит|Платформа|
|7|Срабатывает алерт «API Боцмана недоступен» (на основе healthcheck)|Платформа (дежурный видит, что компонент не отвечает)|
|8|Дежурный платформы открывает инцидент → эскалирует в продуктовую команду Боцмана|Платформа (первичный triage)|
|9|Команда Боцмана анализирует логи своего сервиса, находит проблему (например, закончились IP-адреса в пуле) и исправляет|Продуктовая команда|
